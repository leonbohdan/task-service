### 🎯 Мета завдання

Змоделювати в оперативній пам'яті (in-memory) роботу складеного індексу реляційної бази даних для пошуку товарів за трьома критеріями:

1. `category` (точний збіг `=`)
2. `inStock` (точний збіг `=`)
3. `price` (діапазонний запит `minPrice <= price <= maxPrice`)

---

### 🔬 Порівняння трьох підходів пошуку

```
1. Linear Search O(N)               2. Index + findIndex O(K)           3. Index + Binary Search O(log K)
   [ Прохід по всіх 50k ]              Map.get("electronics:true")         Map.get("electronics:true")
   ┌────────────────────┐              ┌──────────────────────┐             ┌──────────────────────┐
   │ p1, p2, p3 ... pN  │              │ Бакет ~7k елементів  │             │ Бакет ~7k елементів  │
   │ (filter по кожному)│              │ (послідовний пошук)  │             │ (відсортований!)     │
   └────────────────────┘              └──────────────────────┘             └──────────┬───────────┘
   O(N) перевірок                      O(1) + O(K) перевірок                findLowerBound / findUpperBound
                                                                            O(1) + O(log K) перевірок!
```

#### 1. Лінійний пошук (`findProducts`) — $\mathcal{O}(N)$

- **Як працює:** Проходить через увесь масив товарів за допомогою `Array.prototype.filter()` і послідовно перевіряє всі умови для кожного елемента.
- **Аналог у базі даних:** **`Seq Scan` (Sequential Scan)**. База даних змушена послідовно прочитати всі сторінки таблиці з диска або буферного кешу.

#### 2. Композитний хеш-індекс + лінійне сканування бакета (`ProductIndex.query`) — $\mathcal{O}(K)$

- **Як працює:**
  - У конструкторі створюється `Map<string, Product[]>`, де ключ — це складений ключ `${category}:${inStock}`.
  - Точковий пошук бакета виконується за $\mathcal{O}(1)$.
  - Усередині знайденого бакета (де зберігається $K$ товарів конкретної категорії) межі діапазону шукаються лінійним методом `findIndex()`.
- **Аналог у базі даних:** Індекс на частину колонок або Hash-індекс + фільтрація залишкових умов у пам'яті (Recheck Cond).

#### 3. Композитний хеш-індекс + Бінарний пошук (`ProductIndex.binaryQuery`) — $\mathcal{O}(\log K)$

- **Як працює:**
  - Бакет знаходиться миттєво за $\mathcal{O}(1)$.
  - Оскільки при побудові індексу всі товари в кожному бакеті **заздалегідь відсортовані за зростанням `price`**, ліва та права межі діапазону обчислюються бінарним пошуком:
    - `findLowerBound(bucket, minPrice)`: знаходить перший елемент, де `price >= minPrice` за $\mathcal{O}(\log K)$.
    - `findUpperBound(bucket, maxPrice)`: знаходить перший елемент, де `price > maxPrice` за $\mathcal{O}(\log K)$.
  - Повертається точний зріз `bucket.slice(startIndex, endIndex)`.
- **Аналог у базі даних:** Складений **B-Tree Index Scan** на `(category, in_stock, price)` — швидкий пошук кореня/листка (Index Seek) та послідовне зчитування лише потрібного діапазону (Leaf Range Scan).

### 🧠 Архітектурні паралелі з реляційними базами даних

1. **Впорядкованість даних — ключ до ефективних діапазонів:**
   Бінарний пошук принципово неможливий на несортованому масиві. Саме тому реляційні БД обирають **B-Tree** як індекс за замовчуванням (де елементи зберігаються відсортованими), а не Hash-індекси.
2. **Аналогія з правилом лівого префікса:**
   Наш складений ключ `${category}:${inStock}` вимагає точної відповідності обох полів. Якщо в запиті опустити `category`, індекс не зможе вибрати бакет. У B-Tree складеному індексі `(category, inStock, price)` працює та сама логіка: діапазон за `price` можна звузити лише тоді, коли зафіксовані точні рівності на ліві колонки.
3. **Ціна побудови індексу (Write Penalty):**
   - Щоб отримати надшвидкий пошук, у конструкторі `ProductIndex` довелося витратити додатковий час на групування та сортування бакетів $\mathcal{O}(M \cdot K \log K)$, а також виділити додаткову пам'ять під хеш-мапу.
   - Це фундаментальний закон БД: індекси прискорюють читання ціною уповільнення операцій запису (`INSERT`, `UPDATE`) та збільшення обсягу пам'яті (RAM/диск).

## 1. Що таке B-Tree індекс? Чому він є стандартом за замовчуванням у реляційних БД і за яку асимптотичну складність він виконує пошук, вставку та діапазонні запити?

### 📌 Коротке резюме

- **B-Tree (Balanced Tree / самозбалансоване дерево пошуку):** У реляційних БД (зокрема PostgreSQL та MySQL/InnoDB) використовується його різновид — **$B^+$ Tree**. Це розгалужене дерево (високий fan-out), оптимізоване для збереження на блокових носіях (дисках / SSD), де всі листкові вузли (leaves) розташовані на однаковій глибині від кореня, а самі листки зв'язані між собою у двозв'язний список.
- **Чому це стандарт:** Забезпечує надзвичайно пласку структуру (глибина 3–4 рівні на сотні мільйонів рядків) та мінімізує кількість I/O операцій з диска. Крім точкового пошуку (`=`), він підтримує оператори порівняння (`<`, `>`, `<=`, `>=`), сортування (`ORDER BY`), пошук мінімуму/максимуму (`MIN`/`MAX`) та діапазонні запити (`BETWEEN`).
- **Асимптотична складність:**
  - **Точковий пошук (`=`):** $\mathcal{O}(\log N)$
  - **Вставка (`INSERT`):** $\mathcal{O}(\log N)$ _(амортизовано, з урахуванням розщеплення сторінок)_
  - **Видалення (`DELETE`):** $\mathcal{O}(\log N)$
  - **Діапазонні запити (`RANGE SCAN`, `BETWEEN`):** $\mathcal{O}(\log N + K)$, де $N$ — загальна кількість рядків у таблиці, а $K$ — кількість знайдених рядків у діапазоні.

---

### 🔍 Детальний розбір: Як влаштоване $B^+$ Tree

У PostgreSQL модуль `nbtree` реалізує високопродуктивний варіант алгоритму Лемана-Яо (Lehman and Yao) для $B^+$ Tree з високим ступенем паралелізму:

```
                      ┌───────────────────────────────┐
                      │      Root Node (Сторінка 8KB) │
                      │       [ 100  |  500  |  ... ] │
                      └───┬──────────────┬────────┬───┘
                          │              │        │
           ┌──────────────┘              │        └──────────────┐
           ▼                             ▼                       ▼
┌─────────────────────┐       ┌─────────────────────┐       ┌─────────────────────┐
│ Internal Page       │       │ Internal Page       │       │ Internal Page       │
│ [ 20 | 50 | 80 ]    │       │ [ 150 | 250 | 400 ] │       │ [ 600 | 750 | 900 ] │
└──────┬──────────────┘       └──────────┬──────────┘       └──────────────┬──────┘
       │                                 │                                 │
  ┌────┴────────────┐               ┌────┴────────────┐               ┌────┴────────────┐
  ▼                 ▼               ▼                 ▼               ▼                 ▼
┌──────────────┐  ┌──────────────┐┌──────────────┐  ┌──────────────┐┌──────────────┐  ┌──────────────┐
│ Leaf Node    │⇄ │ Leaf Node    ││ Leaf Node    │⇄ │ Leaf Node    ││ Leaf Node    │⇄ │ Leaf Node    │
│ K:V, K:V...  │  │ K:V, K:V...  ││ K:V, K:V...  │  │ K:V, K:V...  ││ K:V, K:V...  │  │ K:V, K:V...  │
│ [TID -> Heap]│  │ [TID -> Heap]││ [TID -> Heap]│  │ [TID -> Heap]││ [TID -> Heap]│  │ [TID -> Heap]│
└──────────────┘  └──────────────┘└──────────────┘  └──────────────┘└──────────────┘  └──────────────┘
  └──────────────────────── Двозв'язний список листків (Doubly-Linked List) ────────────────────────┘
```

#### Ключові особливості внутрішньої структури

1. **Розмір вузла = сторінці бази даних:** Кожен вузол займає рівно один блок (у PostgreSQL за замовчуванням це **8 KB**). Завдяки цьому в одну сторінку вміщуються сотні ключів (високий коефіцієнт розгалуження / _fan-out_ $\approx 100 \dots 500$).
2. **Низька висота (Height) дерева:**
   - За коефіцієнта розгалуження 200 дерево висотою 3 рівні може проіндексувати: $200^3 = 8\,000\,000$ записів.
   - Висота 4 рівні: $200^4 = 1\,600\,000\,000$ (1.6 млрд записів!).
   - Корінь і внутрішні вузли майже гарантовано закешовані в оперативній пам'яті (`shared_buffers`). Отже, для пошуку будь-якого рядка серед мільйонів записів потрібно **лише 1 дискове читання** (читання листкової сторінки).
3. **Розділення даних між внутрішніми та листковими вузлами ($B^+$ Tree):**
   - **Внутрішні вузли (Internal Nodes):** Містять лише ключі-маршрутизатори та посилання на дочірні сторінки дерева. Вони не містять посилань на фізичні рядки таблиці, що дозволяє вмістити максимальну кількість ключів в одну сторінку.
   - **Листкові вузли (Leaf Nodes):** Містять проіндексовані значення та посилання на фізичне розташування рядка в таблиці — **TID (Tuple ID)** у PostgreSQL у форматі `(block_number, tuple_offset)`.
4. **Двозв'язний список на рівні листків:** Листки зв'язані вказівниками «вперед» і «назад». Це ключова перевага над класичним бінарним деревом чи Hash-індексом:
   - Щоб виконати запит `WHERE price BETWEEN 100 AND 500`, база виконує бінарний пошук по дереву за $O(\log N)$ для знаходження першого елемента $\ge 100$, а далі **просто біжить вперед по зв'язаному списку листків**, доки значення не перевищить $500$. Не потрібно повертатися до кореня чи обходити сусідні гілки!

### ⚖️ Порівняння B-Tree з іншими типами індексів

| Тип індексу        | Складність пошуку (`=`) | Діапазони (`<`, `>`, `BETWEEN`)        | Сортування (`ORDER BY`)        | Основне призначення                                                                            |
| :----------------- | :---------------------- | :------------------------------------- | :----------------------------- | :--------------------------------------------------------------------------------------------- |
| **B-Tree**         | $\mathcal{O}(\log N)$   | ✅ **Так** ($\mathcal{O}(\log N + K)$) | ✅ **Так** (дані впорядковані) | **Стандарт за замовчуванням** для 95% задач (ID, числа, дати, рядки).                          |
| **Hash**           | $\mathcal{O}(1)$        | ❌ **Ні**                              | ❌ **Ні**                      | Тільки точні збіги (`=`). Не підтримує складені індекси на діапазони.                          |
| **GiST / SP-GiST** | $\mathcal{O}(\log N)$   | ✅ **Так**                             | ❌ (залежить від оператора)    | Геометрія, координати (PostGIS), повнотекстовий пошук, діапазонні типи (`tsrange`).            |
| **GIN**            | $\mathcal{O}(\log N)$   | ❌ **Ні**                              | ❌ **Ні**                      | Складені типи, JSONB, масиви (`tags @> ARRAY['db']`), повнотекстовий пошук.                    |
| **BRIN**           | $\mathcal{O}(N)$ блоків | ✅ **Так**                             | ❌ **Ні**                      | Величезні таблиці (терабайти), де дані фізично впорядковані в часі (`createdAt`, часові ряди). |

> [!TIP]
> **Чому не Hash-індекс, якщо в нього $\mathcal{O}(1)$?**
> Hash-індекс виконує точковий пошук за $\mathcal{O}(1)$, але він не може допомогти при запитах `WHERE age > 18`, `ORDER BY createdAt`, `WHERE email LIKE 'john%'` або `MIN(price)`. B-Tree є універсальним інструментом, що робить його ідеальним вибором «з коробки».

## 2. Чим `Index Scan` відрізняється від `Bitmap Index Scan` та `Index Only Scan`?

### 📌 Коротке резюме

Ці три стратегії відображають різні підходи оптимізатора PostgreSQL до використання B-Tree індексу в залежності від селективності запиту, наявності потрібних колонок в індексі та вартості дискового читання:

1. **`Index Scan`:** Прямий пошук по індексу. Знайшов ключ $\to$ одразу поліз на диск у таблицю (Heap) за рядком. Ідеально для 1 або декількох рядків (точковий пошук).
2. **`Bitmap Index Scan` + `Bitmap Heap Scan`:** Двоетапний пошук. Спочатку сканує індекс і складає бітову мапу потрібних сторінок таблиці, а потім послідовно вичитує сторінки з таблиці. Перетворює випадкове читання (Random I/O) на послідовне (Sequential I/O).
3. **`Index Only Scan`:** «Святий Грааль» продуктивності. Всі запитувані поля вже є в самому індексі — база взагалі не звертається до таблиці (Heap Fetches = 0).

---

### 🔍 Детальний розбір механік та планів виконання

#### 1. `Index Scan` (Почерговий випадковий доступ)

- **Як працює:** Оптимізатор спускається по B-Tree, знаходить відповідний запис (TID: `BlockId + Offset`) і **миттєво робить звернення до Heap (таблиці)**, щоб прочитати цей рядок. Потім повертається до індексу, бере наступний рядок і знову йде в Heap.
- **Плюси:** Рядки повертаються відразу в порядку сортування індексу. Якщо є `ORDER BY ... LIMIT 10`, виконання зупиняється миттєво після перших 10 знайдених збігів.
- **Мінуси:** При великій кількості рядків спричиняє **Random I/O (випадкове стрибання по диску)**, що дуже дорого для HDD і навіть для SSD при високому навантаженні.

```sql
EXPLAIN ANALYZE SELECT * FROM "Order" WHERE "id" = 'some-uuid';
-- -> Index Scan using "Order_pkey" on "Order" (cost=0.42..8.44 rows=1 width=72)
```

---

#### 2. `Bitmap Index Scan` + `Bitmap Heap Scan` (Пакетне послідовне читання)

Коли за умовою `WHERE` підходить не 1 рядок, а, наприклад, 5 000 із 200 000 (селективність $2\dots 10\%$), звичайний `Index Scan` змусив би диск сотні разів звертатися до одних і тих самих сторінок у хаотичному порядку. Планувальник обирає бітову мапу:

1. **Фаза 1 (`Bitmap Index Scan`):** База сканує індекс і будує в оперативній пам'яті (`work_mem`) **бітову карту (TID Bitmap)**, де кожен біт представляє або конкретний рядок, або сторінку таблиці, яка містить шукані записи.
2. **Фаза об'єднання (за потреби):** Якщо у запиті дві умови з різними індексами (`status = 'PAID' AND totalAmount > 5000`), база може виконати два окремих `Bitmap Index Scan` і провести операцію **`BitmapAnd`** (або `BitmapOr`) просто над бітами в пам'яті без доступу до таблиці!
3. **Фаза 2 (`Bitmap Heap Scan`):** База сортує номери блоків за зростанням і читає купу (Heap) **послідовно (Sequential I/O)**, оминаючи зайві блоки.

```sql
EXPLAIN ANALYZE SELECT * FROM "Order" WHERE "status" = 'PAID';
-- -> Bitmap Heap Scan on "Order"
--      Recheck Cond: ("status" = 'PAID')
--      -> Bitmap Index Scan on idx_orders_status
```

> [!WARNING]
> **Що таке Lossy Bitmap?**
> Якщо розмір бітової карти перевищує виділений ліміт `work_mem`, PostgreSQL перемикається в «неточний» режим (_lossy_): він запам'ятовує не точні позиції рядків, а лише номери сторінок, де є хоча б один збіг. Під час `Bitmap Heap Scan` база змушена перечитувати кожен рядок такої сторінки та повторно перевіряти умову (`Recheck Cond`).

---

#### 3. `Index Only Scan` (Нульове навантаження на Heap)

- **Як працює:** Якщо всі поля, перераховані в `SELECT`, `WHERE`, `JOIN` та `ORDER BY`, входять до складу індексу (або як ключі, або через директиву `INCLUDE`), звертатися до таблиці за даними непотрібно взагалі!
- **Фактор MVCC та Visibility Map:**
  - У PostgreSQL версії рядків (xmin/xmax для ізоляції транзакцій) зберігаються в Heap, а не в індексі.
  - Щоб переконатися, що знайдений в індексі рядок не був видалений або змінений іншою паралельною транзакцією, PostgreSQL звертається до **Visibility Map (VM)** таблиці.
  - Якщо відповідна сторінка таблиці позначена у VM як _all-visible_ (очищена `VACUUM` і не містить незафіксованих змін), звернення до Heap не відбувається (`Heap Fetches: 0`).
  - Якщо сторінка "брудна", базі все одно доведеться звернутися до Heap (`Heap Fetches > 0`).

```sql
-- Створюємо складений індекс або індекс із INCLUDE:
CREATE INDEX idx_orders_covering ON "Order" ("userId", "status") INCLUDE ("totalAmount");

-- Запит бере лише поля, які є в індексі:
EXPLAIN ANALYZE
SELECT "userId", "status", "totalAmount" FROM "Order"
WHERE "userId" = 'u1' AND "status" = 'PAID';

-- -> Index Only Scan using idx_orders_covering on "Order" (Heap Fetches: 0)
```

---

### 📊 Порівняльна матриця трьох типів сканування

| Параметр                         | `Index Scan`                                  | `Bitmap Index Scan`                                                      | `Index Only Scan`                                |
| :------------------------------- | :-------------------------------------------- | :----------------------------------------------------------------------- | :----------------------------------------------- |
| **Доступ до Heap (таблиці)**     | Для кожного рядка окремо (Random I/O)         | Пакетний за відсортованими блоками (Sequential I/O)                      | Відсутній (або мінімальний через Visibility Map) |
| **Збереження сортування B-Tree** | ✅ **Так** (не потрібен окремий вузол `Sort`) | ❌ **Ні** (сортування втрачається через сортування за фізичними блоками) | ✅ **Так**                                       |
| **Об'єднання кількох індексів**  | ❌ Ні                                         | ✅ **Так** (`BitmapAnd` / `BitmapOr`)                                    | ❌ Ні                                            |
| **Оптимальна селективність**     | Висока ($< 1\%$ рядків, `LIMIT`, `PK`)        | Середня ($2\% \dots 20\%$ рядків)                                        | Будь-яка (де всі колонки покриті індексом)       |

## 3. Правило лівого префікса: Якщо індекс створено на `(A, B, C)`, які комбінації в блоці `WHERE` зможуть його використати, а які — ні?

### 📌 Коротке резюме

- **Складений індекс (Composite Index)** сортує дані послідовно: спочатку за колонкою `A`. Якщо значення `A` однакові — вони сортуються за `B`. Якщо однакові й `A`, і `B` — сортуються за `C`.
- **Правило лівого префікса (Leftmost Prefix Rule):** Індекс може ефективно використовуватися пошуковим алгоритмом B-Tree **тільки тоді, коли в запиті присутній безперервний ланцюжок колонок, починаючи з крайньої лівої (`A`)**.
- Якщо пропустити проміжну колонку (наприклад, шукати за `A` та `C`, пропустивши `B`), то колонка `A` спрацює для бінарного пошуку в дереві, але колонка `C` не зможе виконати прямий стрибок (seek) — вона перевірятиметься як звичайний залишковий фільтр над знайденими вузлами.

---

### 🔍 Аналогія з телефонним довідником

Уявіть класичний телефонний довідник, де записи відсортовані за трьома полями:
`[Прізвище (A)] ➔ [Ім'я (B)] ➔ [По батькові (C)]`

```
Іваненко  |  Андрій   |  Васильович
Іваненко  |  Богдан   |  Олегович
Іваненко  |  Богдан   |  Петрович
Петренко  |  Андрій   |  Сергійович
```

1. **Чи можна знайти людей з прізвищем «Іваненко»?**
   - ✅ **Так!** Ми миттєво відкриваємо букву «І» за $O(\log N)$.
2. **Чи можна знайти людей «Іваненко Богдан»?**
   - ✅ **Так!** Знаходимо блок «Іваненко» і всередині нього миттєво знаходимо блок «Богдан».
3. **Чи можна знайти всіх людей з ім'ям «Богдан» без прізвища?**
   - ❌ **Ні!** Люди з ім'ям «Богдан» розпорошені по всьому довіднику: є і в Іваненка, і в Коваленка, і в Шевченка. Доведеться перегорнути весь довідник від початку до кінця (`Seq Scan` / `Full Index Scan`).

---

### 📋 Матриця комбінацій умов `WHERE` для індексу `(A, B, C)`

|   №   | Умова в блоці `WHERE`             | Використання B-Tree індексу | Як саме виконується запит                                                                                                                                  |
| :---: | :-------------------------------- | :-------------------------: | :--------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1** | `WHERE A = 1`                     |  ✅ **Повне (префікс A)**   | Швидкий `Index Seek` за деревом за першою колонкою.                                                                                                        |
| **2** | `WHERE A = 1 AND B = 2`           | ✅ **Повне (префікс A, B)** | Двокроковий `Index Seek` за першими двома колонками.                                                                                                       |
| **3** | `WHERE A = 1 AND B = 2 AND C = 3` | ✅ **Повне (всі колонки)**  | Максимально точний `Index Seek` за всіма трьома рівнями.                                                                                                   |
| **4** | `WHERE B = 2 AND A = 1`           |        ✅ **Повне**         | **Порядок у `WHERE` не має значення!** Оптимізатор SQL (CBO) автоматично переставляє предикати під порядок індексу.                                        |
| **5** | `WHERE A = 1 AND C = 3`           | ⚠️ **Часткове (Тільки A)**  | `A` використовується як `Index Condition` (звужує діапазон у дереві). Поле `C` працює лише як вторинний `Filter` над отриманими рядками, бо `B` відсутній. |
| **6** | `WHERE B = 2`                     | ❌ **Не використовується**  | Порушено правило лівого префікса. Планувальник обере `Seq Scan` (повне сканування таблиці).                                                                |
| **7** | `WHERE C = 3`                     | ❌ **Не використовується**  | Порушено правило лівого префікса (`Seq Scan`).                                                                                                             |
| **8** | `WHERE B = 2 AND C = 3`           | ❌ **Не використовується**  | Префікс `A` відсутній — індекс непридатний для пошуку (`Seq Scan`).                                                                                        |

### ⚡ Вплив діапазонних операторів (`<`, `>`, `BETWEEN`, `LIKE`)

Якщо в запиті для якоїсь колонки використовується **діапазонний оператор**, наступні колонки індексу вже **не можуть використовуватися для прямого пошуку (Seek)**!

#### Приклад

```sql
-- Індекс створено на (status, createdAt, totalAmount)
SELECT * FROM "Order"
WHERE "status" = 'PAID'
  AND "createdAt" >= '2026-01-01'
  AND "totalAmount" > 1000;
```

- `"status" = 'PAID'` — точна рівність $\to$ **Index Seek**.
- `"createdAt" >= '2026-01-01'` — діапазон $\to$ **Index Seek** (знаходить початкову дату і сканує листки праворуч).
- `"totalAmount" > 1000` — **НЕ може брати участь у звуженні діапазону в B-Tree!** Для кожного знайденого замовлення зі статусом `PAID` і датою $\ge$ 2026-01-01 поле `totalAmount` перевіряється звичайним фільтром, оскільки всередині діапазону дат суми замовлень не відсортовані глобально.

> [!IMPORTANT]
> **Золоте правило проєктування складених індексів:**
>
> 1. На перші позиції (ліворуч) завжди ставте колонки з **точною рівністю (`=`)** та високою селективністю.
> 2. Далі ставте колонки, за якими виконується **діапазонна фільтрація (`<`, `>`, `BETWEEN`)**.
> 3. Наприкінці ставте колонки, за якими виконується сортування **`ORDER BY`**, щоб уникнути дорогої фази `Sort` у плані запиту.

## 4. Ціна індексів: Якщо індекси так прискорюють читання, чому ми просто не індексуємо кожну колонку таблиці?

### 📌 Коротке резюме

Індекси в базі даних — це класичний архітектурний компроміс (Trade-off) між **швидкістю читання (Read throughput)** та **швидкістю запису (Write throughput)**, використанням дискового простору й оперативної пам'яті. Якщо проіндексувати кожну колонку, база даних миттєво втратить продуктивність на операціях `INSERT`, `UPDATE`, `DELETE`, роздується в розмірах (Bloat) і паралізує роботу фонових процесів обслуговування (`VACUUM`).

---

### 🔍 Чотири основні фактори вартості надлишкової індексації

```
                ┌───────────────────────────────────────────┐
                │   ЦІНА НАДЛИШКОВОЇ ІНДЕКСАЦІЇ             │
                └─────────────────────┬─────────────────────┘
         ┌──────────────────┬─────────┴─────────┬──────────────────┐
         ▼                  ▼                   ▼                  ▼
┌─────────────────┐┌─────────────────┐┌─────────────────┐┌─────────────────┐
│ 1. Деградація   ││ 2. Споживання   ││ 3. Навантаження ││ 4. Затримки     │
│ операцій запису ││ пам'яті та диска││ на Autovacuum   ││ планувальника   │
│ (Write Penalty) ││ (RAM / Cache)   ││ та реплікацію   ││ (Planning Time) │
└─────────────────┘└─────────────────┘└─────────────────┘└─────────────────┘
```

#### 1. Деградація операцій запису (Write Amplification)

- **`INSERT`:** При вставці одного рядка база повинна записати дані в саму таблицю (Heap) **плюс у кожне B-Tree дерево**. Якщо на таблиці створено 10 індексів, один `INSERT` перетворюється на **11 окремих операцій запису**.
- **Розщеплення сторінок (B-Tree Page Split):** Якщо сторінка індексу (8 KB) заповнена, вставка нового значення вимагає:
  1. Алокації нової сторінки на диску.
  2. Перенесення половини записів зі старої сторінки в нову.
  3. Оновлення посилань у батьківському вузлі та в сусідніх листках.
     Це призводить до різких стрибків затримки (latency spikes) під час запису.
- **`UPDATE` та блокування оптимізації HOT (Heap-Only Tuples):**
  - У PostgreSQL є надважлива оптимізація: якщо оновлюються поля, які **НЕ входять до жодного індексу**, новий рядок записується в ту саму сторінку таблиці без необхідності оновлювати індекси (**HOT Update**).
  - Якщо ж проіндексувати майже всі колонки, кожен `UPDATE` змушений оновлювати індекси, що породжує лавиноподібне розростання dead tuples і дискового I/O.

---

#### 2. Споживання дискового простору та витіснення кешу (RAM & Cache Footprint)

- **Розмір індексів перевищує розмір даних:** Дуже часто сумарний обсяг 7–10 індексів на великій таблиці у 2–3 рази перевищує обсяг самої таблиці з даними.
- **Виснаження `shared_buffers` (Buffer Pool Thrashing):**
  - Щоб індекс працював блискавично, його дерево має повністю або частково лежати в оперативній пам'яті.
  - Якщо індексів забагато, вони починають конкурувати за пам'ять з самими даними таблиці, витісняючи корисні гарячі дані з кешу. В результаті база починає постійно вичитувати блоки з повільного диска.

---

#### 3. Навантаження на фонові процеси (Autovacuum, Wal, Backup, Replication)

- **Важкий `AUTOVACUUM`:** Під час очищення мертвих рядків (dead tuples) процес vacuum повинен просканувати та очистити **кожен індекс окремо**. Багато індексів призводять до того, що vacuum працює безперервно, споживаючи I/O ліміти сервера.
- **Збільшення обсягу WAL (Write-Ahead Log):** Кожне розщеплення сторінки індексу та кожне оновлення B-Tree генерує додаткові записи у WAL. Це збільшує мережевий трафік на репліки та уповільнює процес створення бекапів (`pg_dump` / WAL archiving).

---

#### 4. Ускладнення роботи планувальника запитів (Query Planner Overhead)

- Планувальник PostgreSQL (**Cost-Based Optimizer, CBO**) при аналізі запиту перебирає можливі шляхи доступу до даних.
- Коли таблиця має десятки індексів, оптимізатор витрачає значний час на комбінаторний розрахунок вартості кожного варіанта.
- У високонавантажених OLTP-системах, де запит має виконуватися за 1–2 мс, час планування (**Planning Time**) може скласти 5–10 мс, перевищуючи сам час виконання (**Execution Time**)!
- Зростає ризик того, що через похибки в статистиці планувальник обере неоптимальний індекс.

### 💡 Як приймати рішення щодо створення індексу

```
Чи потрібен індекс?
 ├── Це Primary Key або Foreign Key? ──────────────► ТАК (PK автоматично, FK обов'язково індексуємо вручну)
 ├── Запит виконується часто (OLTP hot-path)? ─────► ТАК (створюємо під конкретний WHERE / ORDER BY)
 ├── Низька селективність (наприклад, boolean)? ───► НІ (база все одно обере Seq Scan)
 ├── Потрібна лише частина даних (status = 'PENDING')? ► ТАК (використовуємо Partial Index: WHERE status = 'PENDING')
 └── Таблиця переважно для запису (Log / Audit)? ──► НІ (мінімум або жодних індексів, крім часу/PK)
```

> [!TIP]
> **Часткові індекси (Partial Indexes) як порятунок від роздутих B-Tree:**
> Замість індексації всієї колонки створюйте індекс лише на ті рядки, які дійсно шукаються. Наприклад, якщо 99% замовлень мають статус `COMPLETED`, а бекенд постійно шукає лише активні замовлення в черзі:
>
> ```sql
> CREATE INDEX idx_orders_active_queue ON "Order" ("createdAt")
> WHERE "status" = 'PENDING';
> ```
>
> Такий індекс займатиме лічені кілобайти пам'яті замість гігабайтів і практично не сповільнюватиме операції запису для завершених замовлень!
