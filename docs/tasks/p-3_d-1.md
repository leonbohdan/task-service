## 🧩 Завдання 1: Алгоритмічний розігрів (Exponential Backoff with Jitter)

### Мета

Реалізувати на TypeScript універсальну функцію обгортки асинхронних операцій `retryWithBackoff<T>`, яка автоматично повторює ненадійний мережевий виклик з експоненційним збільшенням інтервалу та додаванням випадкового розкиду (Full Jitter).

### Чому Jitter критично важливий?

Якщо зовнішній сервіс або база даних падає, сотні клієнтів одночасно отримують помилку. Якщо всі вони повторюють запит через фіксовані інтервали (наприклад, рівно через 1с, потім через 2с, потім через 4с), вони синхронізуються у фазі та б'ють по сервісу хвилями однакової амплітуди. Це явище називається **Thundering Herd Problem** (або ефект натовпу) і гарантовано добиває сервіс, що намагається піднятися.

Формула розрахунку інтервалу з **Full Jitter**:
$$t_{\text{sleep}} = \text{random}(0, \min(\text{maxDelay}, \text{baseDelay} \times 2^{\text{attempt}}))$$

### Вимоги до реалізації

1. **Типізація та конфігурація:**
   Створи функцію із наступним інтерфейсом:

   ```typescript
   export interface RetryOptions {
     maxRetries: number;      // Максимальна кількість повторних спроб (наприклад, 4)
     baseDelayMs: number;     // Початкова затримка в мілісекундах (наприклад, 200)
     maxDelayMs: number;      // Верхня межа затримки (наприклад, 3000)
     shouldRetry?: (error: unknown) => boolean; // Фільтр помилок (наприклад, не повторювати 400 Bad Request)
   }

   export async function retryWithBackoff<T>(
     operation: (attempt: number) => Promise<T>,
     options: RetryOptions,
   ): Promise<T>;
   ```

2. **Вимоги до поведінки:**
   - Якщо операція виконана успішно з першої або наступної спроби, повертається її результат.
   - Якщо операція викидає помилку:
     - Перевіряється `shouldRetry(error)`. Якщо повертає `false` — негайно прокидається вихідна помилка без очікування.
     - Якщо спроби вичерпано (`attempt >= maxRetries`), прокидається остання отримана помилка.
     - Інакше розраховується експоненційна пауза з випадковим рандомізованим відхиленням, викликається асинхронний сон (`setTimeout`) і операція запускається знову.

### Шаблон для перевірки

```typescript
async function testRetryUtility() {
  let callCount = 0;

  // Симуляція ненадійного мережевого запиту: перші 3 спроби падають з Network Error
  const flakyNetworkCall = async (attempt: number) => {
    callCount++;
    console.log(`[Спроба #${attempt + 1}] Виклик операції о ${new Date().toISOString().substring(17, 23)}...`);
    if (callCount < 3) {
      const err = new Error("503 Service Unavailable");
      (err as any).statusCode = 503;
      throw err;
    }
    return { status: 200, data: "Успішна відповідь!" };
  };

  console.log("--- Тестування retryWithBackoff ---");
  const startTime = Date.now();

  const result = await retryWithBackoff(flakyNetworkCall, {
    maxRetries: 4,
    baseDelayMs: 150,
    maxDelayMs: 2000,
    shouldRetry: (err: any) => err.statusCode === 503,
  });

  const totalDuration = Date.now() - startTime;
  console.log(`Результат:`, result);
  console.log(`Всього спроб: ${callCount}, загальний час очікування: ${totalDuration}ms`);
  console.assert(callCount === 3, "Мало бути рівно 3 спроби!");
  console.log("✅ Алгоритм Exponential Backoff + Jitter працює коректно!");
}

testRetryUtility();
```

## 🛠️ Завдання 2: Об'єднання сервісів у спільну мережу Docker Compose

### Мета

Об'єднати сервіси системи у спільну ізольовану bridge-мережу Docker Compose, забезпечити взаємний резолвінг імен сервісів через вбудований Docker DNS та налаштувати коректний порядок запуску за допомогою перевірок готовності (`healthcheck`).

### Архітектура системи

1. **`order-service`** (NestJS + PostgreSQL) — сервіс створення та управління замовленнями (порт 3000).
2. **`analytics-service`** (NestJS + MongoDB) — аналітичний сервіс звітів (порт 3001).
3. **`notification-service`** (NestJS / Node.js) — новий легкий мікросервіс надсилання сповіщень клієнтам (порт 3002).

```
         +-------------------------------------------------------+
         |             Docker Network: microservices_net         |
         |                                                       |
         |   +---------------+              +----------------+   |
         |   | order-service | -----------> | analytics-svc  |   |
         |   +---------------+   (HTTP/REST)| +--------------+   |
         |           |                      | |   MongoDB    |   |
         |           |                      | +--------------+   |
         |           | (HTTP/REST)                               |
         |           v                                           |
         |   +-------------------+                               |
         |   | notification-svc  |                               |
         |   +-------------------+                               |
         +-------------------------------------------------------+
```

### Кроки реалізації

1. **Створення сервісу `notification-service`:**
   Створи мінімальний NestJS/Express додаток для обробки сповіщень з ендпоінтом:
   `POST /notifications/send` $\rightarrow$ приймає `{ orderId, customerEmail, message }`, логує відправку в консоль та повертає `{ status: 'SENT', sentAt: new Date() }`.

2. **Написання загального `docker-compose.microservices.yml`:**
   Створи файл оркестрації в корені проєкту:

   ```yaml
   version: '3.8'

   networks:
     microservices_net:
       driver: bridge

   services:
     postgres-db:
       image: postgres:16-alpine
       environment:
         POSTGRES_USER: user
         POSTGRES_PASSWORD: password
         POSTGRES_DB: order_db
       healthcheck:
         test: ["CMD-SHELL", "pg_isready -U user -d order_db"]
         interval: 5s
         timeout: 5s
         retries: 5
       networks:
         - microservices_net

     mongodb:
       image: mongo:7.0
       healthcheck:
         test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
         interval: 5s
         timeout: 5s
         retries: 5
       networks:
         - microservices_net

     notification-service:
       build:
         context: ./notification-service
         dockerfile: Dockerfile
       ports:
         - "3002:3002"
       networks:
         - microservices_net

     analytics-service:
       build:
         context: ./analytics-service
         dockerfile: Dockerfile
       ports:
         - "3001:3001"
       environment:
         MONGO_URI: mongodb://mongodb:27017/insight_pulse
       depends_on:
         mongodb:
           condition: service_healthy
       networks:
         - microservices_net

     order-service:
       build:
         context: ./order-service
         dockerfile: Dockerfile
       ports:
         - "3000:3000"
       environment:
         DATABASE_URL: postgresql://user:password@postgres-db:5432/order_db
         ANALYTICS_SERVICE_URL: http://analytics-service:3001
         NOTIFICATION_SERVICE_URL: http://notification-service:3002
       depends_on:
         postgres-db:
           condition: service_healthy
       networks:
         - microservices_net
   ```

3. **Перевірка DNS-резолвінгу:**
   Запусти систему: `docker compose -f docker-compose.microservices.yml up -d`.
   Зайди всередину контейнера `order-service`:
   ```bash
   docker exec -it <order_container_id> sh
   # Перевір зв'язок за назвами сервісів замість localhost:
   ping notification-service
   curl http://analytics-service:3001/health
   ```

## 💥 Завдання 3: Анатомія лавиноподібної відмови (Cascading Failure при синхронному HTTP)

### Мета

На практиці відтворити та проаналізувати головний фатальний недолік мікросервісної архітектури, зв'язаної жорсткими синхронними HTTP-запитами: блокування пулу потоків/з'єднань, деградація чуйності всієї системи та відмова головного бізнес-процесу при збої другорядного сервісу.

### Кроки експерименту

1. **Реалізація синхронного ланцюжка у `order-service`:**
   При виклику `POST /orders` (створення замовлення):
   - Крок 1: Замовлення зберігається в базі даних PostgreSQL.
   - Крок 2: Синхронний виклик `HttpService.post('http://analytics-service:3001/events', ...)` для реєстрації події аналітики.
   - Крок 3: Синхронний виклик `HttpService.post('http://notification-service:3002/notifications/send', ...)` для відправки email клієнту.
   - Крок 4: Повернення клієнту статусу `201 Created`.

2. **Моделювання збою інфраструктури:**
   - **Сценарій А (Повільний сервіс сповіщень):** Додай у `notification-service` штучну затримку в 10 секунд (`await sleep(10000)`).
   - Запусти навантажувальний тест на `POST /orders` (наприклад, 50 запитів через `autocannon` або Apache Benchmark: `ab -n 50 -c 10 http://localhost:3000/orders`).
   - Зафіксуй поведінку: час створення замовлення для користувача злітає до 10+ секунд, черга HTTP socket'ів Node.js переповнюється, пам'ять росте.
   - **Сценарій Б (Повне падіння сервісу сповіщень):** Зупини контейнер `notification-service` (`docker stop <notification_container_id>`).
   - Відправ `POST /orders`.
   - Зафіксуй критичний збій: клієнт отримує помилку `500 Internal Server Error`, замовлення не створено (або створено в БД, але користувач вважає операцію проваленою), бізнес втрачає конверсію через падіння необов'язкового сповіщення!

3. **Аналіз результатів:**
   Сформулюй висновки: чому другорядні операції (аналітика, сповіщення, аудит) категорично **не повинні** виконуватися у синхронному життєвому циклі основного бізнес-запиту, і як перехід на асинхронні черги подій (Event-Driven) повністю усуває цю вразливість.

## 🎯 Питання для самоперевірки та інтерв'ю

1. **Теорема CAP у реальних мікросервісних системах:**
   Чому в розподілених мережах неможливо відмовитися від складової Partition Tolerance ($P$)? Між чим насправді змушений обирати архітектор під час мережевого збою ($CP$ vs $AP$) і якою системою за класифікацією CAP є типова e-commerce мережа?

2. **Антипатерн "Розподілений моноліт" (Distributed Monolith):**
   За якими ознаками архітектуру з кількома мікросервісами можна діагностувати як "розподілений моноліт"? Чому синхронні виклики через REST/HTTP між сервісами часто призводять до найгіршого з обох світів (складність мікросервісів + жорстка зв'язаність моноліту)?

3. **Розподілені транзакції: Two-Phase Commit (2PC) проти Saga:**
   Чому класичний протокол двофазної фіксації (2PC) вважається антипатерном у масштабованих мікросервісах (блокування ресурсів, координатор як єдина точка відмови)? Як патерн Saga вирішує проблему узгодженості через локальні транзакції та компенсуючі дії (Compensating Transactions)?

4. **Saga Orchestration vs Saga Choreography:**
   У чому полягає фундаментальна різниця між оркестрацією (наявність центрального керуючого сервісу/оркестратора) та хореографією (сервіси слухають події один одного) у патерні Saga? Які переваги та ризики кожного підходу для високонавантаженого бізнесу?
