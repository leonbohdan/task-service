### 🔬 Суть проблеми: Стан гонитви (Race Condition) у Node.js

Існує поширена омана, що однопотоковість виконання JavaScript у Node.js унеможливлює стан гонитви. На рівні виконання процесорних інструкцій код дійсно виконується послідовно. Проте стан гонитви виникає на рівні **бізнес-логіки**, коли складна операція переривається асинхронними паузами (`await`).

Операція списання коштів або резервування товару є класичним патерном **Check-Then-Act (Read-Modify-Write)**:
1. **Read & Check:** перевірити, чи баланс/залишок достатній (`balance >= amount`).
2. **I/O Wait:** асинхронна операція (запит до БД, звернення до платіжного шлюзу, таймер).
3. **Write:** оновити стан (`balance -= amount`).

#### Хронологія гонитви без блокування:

```
Час (t)   Потік виконання (Event Loop)                                    Спільний баланс
───────   ─────────────────────────────────────────────────────────────   ───────────────
t0        Запит 1: перевіряє (100 >= 80) -> true                          balance = 100
t1        Запит 1: викликає await setTimeout(50) і ВІДПУСКАЄ ПОТІК        balance = 100
t2        Запит 2: отримує вільний потік, перевіряє (100 >= 80) -> true  balance = 100
t3        Запит 2: викликає await setTimeout(50) і ВІДПУСКАЄ ПОТІК        balance = 100
t4 (50ms) Запит 1: прокидається, списує balance -= 80                     balance = 20
t5 (50ms) Запит 2: прокидається, списує balance -= 80                     balance = -60 💥
```

> [!WARNING]
> **Ключовий висновок:** `await` розриває атомарність операції. Доки перший запит чекає на відповідь зовнішнього ресурсу, інший запит зчитує застарілий стан (Stale Read), що веде до аномалії втраченого оновлення (Lost Update) або некоректного від'ємного балансу.

### 🛠️ Архітектура та реалізація Mutex

**Mutex (Mutual Exclusion)** — це примітив синхронізації, що гарантує, що лише один потік керування може одночасно знаходитися всередині критичної секції.

У файлі [index.day_5.ts](file:///home/bohdan/MyProjects/test_projects/task-service/index.day_5.ts) ми реалізували та дослідили два підходи:

#### 1. Класичний Mutex на базі масиву очікування (`queue`)

```typescript
class Mutex {
  private locked = false;
  private queue: (() => void)[] = [];

  async acquire(): Promise<() => void> {
    const release = () => {
      if (this.queue.length > 0) {
        // Передаємо замок наступному в черзі, locked залишається true
        const next = this.queue.shift();
        if (next) next();
      } else {
        // Якщо черга порожня — відкриваємо замок для нових звернень
        this.locked = false;
      }
    };

    if (!this.locked) {
      this.locked = true;
      return release;
    }

    // Замок зайнятий: зберігаємо resolve у чергу очікування
    await new Promise<void>((resolve) => {
      this.queue.push(resolve);
    });

    return release;
  }

  async runExclusive<T>(callback: () => Promise<T>): Promise<T> {
    const release = await this.acquire();
    try {
      return await callback();
    } finally {
      release(); // Гарантоване звільнення навіть при помилці
    }
  }
}
```

- **Механіка черги:** Замість блокуючого очікування процесора, ми створюємо `new Promise<void>`, а його функцію `resolve` додаємо до масиву `queue`. Потік залишається повністю неблокованим для інших подій Event Loop.
- **Гарантія FIFO:** Функції `resolve` витягуються через `shift()`, забезпечуючи сувору черговість викликів у порядку надходження (First-In, First-Out).

#### 2. Альтернатива: Promise Chaining (`MutexChained`)

Альтернативний функціональний патерн «естафетної палички», де черга очікування формується не явним масивом, а неявним ланцюжком `.then()` у черзі мікротасок рушія V8:

```typescript
class MutexChained {
  private current: Promise<void> = Promise.resolve();

  async acquire(): Promise<() => void> {
    let release!: () => void;
    const next = new Promise<void>((resolve) => {
      release = resolve;
    });

    const wait = this.current;
    this.current = this.current.then(() => next);

    await wait;
    return release;
  }
}
```

### 🛡️ Навіщо потрібен `runExclusive` і чому важливий `try...finally`

Ручне використання `acquire()` та `release()` є небезпечним через ризик виникнення **Deadlock**:

```typescript
// ❌ НЕБЕЗПЕЧНО:
const release = await mutex.acquire();
await riskyOperation(); // Якщо тут станеться throw new Error() — release() ніколи не викличеться!
release();
```

Якщо `release()` не буде викликано, замок назавжди залишиться заблокованим, а всі наступні запити в системі зависнуть у черзі.

Метод `runExclusive` вирішує цю проблему завдяки блоку `try...finally`:
1. Блок `finally` **гарантовано виконується завжди** — як при успішному поверненні результату, так і при перехопленні виключення.
2. Конструкція `return await callback()` є обов'язковою: без ключового слова `await` проміс повернеться негайно, блок `finally` виконається до завершення асинхронної операції, і критична секція відкриється завчасно.

## 1. ACID: Розкрий значення кожної літери простими словами на прикладі банківського переказу

### 📌 Коротке резюме

**ACID** — це набір фундаментальних вимог до транзакційної СУБД, що гарантують надійність та передбачуваність даних у неідеальних умовах (збої живлення, падіння серверів, паралельні клієнтські запити).

| Літера | Властивість | Суть у трьох словах | Поведінка при збої |
| :--- | :--- | :--- | :--- |
| **A** | **Atomicity** (Атомарність) | «Все або нічого» | Повний відкат (`ROLLBACK`) усіх кроків при збої хоча б одного. |
| **C** | **Consistency** (Узгодженість) | «Тільки валідні стани» | Захист інваріантів системи (`CHECK`, `FK`, бізнес-правила балансу). |
| **I** | **Isolation** (Ізольованість) | «Ніби транзакція одна» | Паралельні операції не бачать незавершених чернеток одна одної. |
| **D** | **Durability** (Довговічність) | «Закомітив — збереглося назавжди» | Гарантія збереження на диску (WAL) навіть при знеструмленні. |

### 🔬 Детальний розбір на прикладі переказу 100 грн від Аліси до Боба

Сценарій: Аліса переказує 100 грн Бобу. Це дві SQL-операції:
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'Alice'; -- Крок 1
UPDATE accounts SET balance = balance + 100 WHERE id = 'Bob';   -- Крок 2
COMMIT;
```

#### 1. Atomicity (Атомарність)
- **Проблема:** Якщо сервер впаде після Кроку 1, але до Кроку 2, з Аліси зніметься 100 грн, а Бобу нічого не надійде — гроші просто «зникнуть» у повітрі.
- **Як захищає СУБД:** Усі операції всередині транзакції є неподільним цілим. Якщо стається будь-яка помилка, збій мережі або падіння бази даних, база автоматично виконує `ROLLBACK`. Зміни повертаються до вихідного стану: або обидва рахунки оновлено, або жоден.

#### 2. Consistency (Узгодженість)
- **Проблема:** У системі є правило (інваріант): баланс не може бути від'ємним (`CHECK (balance >= 0)`), а загальна грошова маса в системі після переказу має залишитися незмінною (`Sum_before == Sum_after`).
- **Як захищає СУБД:** Транзакція переводить базу з одного валідного стану в інший валідний стан. Якщо в Аліси було лише 50 грн, спроба списати 100 викличе помилку констрейнту бази даних, транзакція буде анульована, і база ніколи не збереже стан із балансом `-50`.

#### 3. Isolation (Ізольованість)
- **Проблема:** У той самий момент, коли Аліса переказує гроші, головний бухгалтер запускає аудиторський звіт із підрахунком суми грошей на всіх рахунках банку (`SELECT SUM(balance) FROM accounts;`).
- **Як захищає СУБД:** Бухгалтер не повинен побачити "проміжний" неконсистентний стан, де з Аліси вже списали, а Бобу ще не зарахували. Для бухгалтера операція або ще взагалі не почалася, або вже повністю завершилася.

#### 4. Durability (Довговічність / Надійність)
- **Проблема:** Клієнт отримав статус: *"Переказ успішно виконано (HTTP 200 / COMMIT OK)"*, але через 1 мілісекунду в дата-центрі вирубало електрику.
- **Як захищає СУБД:** Після успішного `COMMIT` дані гарантовано скинуті в енергонезалежну пам'ять (диск/SSD) через журнал попереднього запису (**Write-Ahead Log / WAL**) за допомогою системного виклику `fsync`. Навіть після перезавантаження сервера гроші Боба залишаться на його рахунку.

## 2. Рівні ізоляції SQL стандарту: Назви 4 рівні ізоляції від найслабшого до найсуворішого. Які аномалії допускає кожен із них?

### 📌 Класичні 3 аномалії стандарту ANSI SQL-92

1. **Dirty Read (Брудне читання):** Транзакція B читає незафіксовані (uncommitted) зміни Транзакції A. Якщо Транзакція A згодом робить `ROLLBACK`, Транзакція B працювала з "даними-привидами", яких ніколи не існувало.
2. **Non-repeatable Read (Неповторюване / Розмите читання):** Транзакція A читає рядок. Транзакція B змінює (`UPDATE`) або видаляє (`DELETE`) цей же рядок і робить `COMMIT`. Транзакція A читає той самий рядок повторно і бачить зовсім інші значення.
3. **Phantom Read (Фантомне читання):** Транзакція A зчитує набір рядків за діапазоном (наприклад, `WHERE price BETWEEN 10 AND 50`). Транзакція B вставляє (`INSERT`) новий товар із `price = 30` і робить `COMMIT`. При повторному діапазонному запиті Транзакція A виявляє новий рядок («фантом»).

---

### 📊 Матриця ізоляції стандарту ANSI SQL-92

| Рівень ізоляції (від слабшого до суворішого) | Dirty Read | Non-repeatable Read | Phantom Read |
| :--- | :---: | :---: | :---: |
| **1. READ UNCOMMITTED** | ❌ Допускає | ❌ Допускає | ❌ Допускає |
| **2. READ COMMITTED** *(дефолт у PostgreSQL)* | ✅ Захищає | ❌ Допускає | ❌ Допускає |
| **3. REPEATABLE READ** *(дефолт у MySQL InnoDB)* | ✅ Захищає | ✅ Захищає | ❌ Допускає (за стандартом) |
| **4. SERIALIZABLE** | ✅ Захищає | ✅ Захищає | ✅ Захищає |

---

### 💡 Важливий нюанс PostgreSQL (MVCC реальність на співбесіді):

Реалізація рівнів ізоляції в сучасних СУБД (зокрема PostgreSQL) через механізм версіонування рядків (**MVCC — Multi-Version Concurrency Control**) суворіша, ніж того вимагав старий стандарт ANSI:

1. **`READ UNCOMMITTED` у PostgreSQL відсутній:** Якщо ви вкажете `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;`, PostgreSQL автоматично інтерпретує це як `READ COMMITTED`. Читання "брудних" (незакомічених) даних у PostgreSQL неможливе архітектурно, бо кожен запит бачить лише закомічені снепшоти.
2. **`REPEATABLE READ` у PostgreSQL блокує також і Phantom Read!** Завдяки снепшоту на початку транзакції, повторний діапазонний `SELECT` ніколи не покаже нових вставлених рядків.
3. **Навіщо тоді `SERIALIZABLE` у PostgreSQL?** Він захищає від складніших аномалій — зокрема **Write Skew** (викривлення запису), де дві паралельні транзакції читають перехресні дані й одночасно вносять несумісні зміни, порушуючи бізнес-правило. PostgreSQL реалізує це через **SSI (Serializable Snapshot Isolation)** без важких блокувань на читання.

## 3. Pessimistic vs Optimistic Locking: За якими критеріями обрати песимістичне або оптимістичне блокування?

| Параметр порівняння | Песимістичне блокування (Pessimistic) | Оптимістичне блокування (Optimistic) |
| :--- | :--- | :--- |
| **Філософія** | *«Конфлікт дуже ймовірний, тому я заблокую запис від усіх, доки не закінчу».* | *«Конфлікти рідкісні, тому я нічого не блокую, а перед записом перевірю версію».* |
| **SQL реалізація** | `SELECT ... FOR UPDATE` | `UPDATE ... WHERE id = $id AND version = $v` |
| **Накладні витрати** | Утримання фізичних блокувань рядків у СУБД, споживання з'єднань пулу. | Додаткова колонка `version`, логіка повторних спроб (retry). |
| **Поведінка при конфлікті** | Інші запити чекають у черзі блокування. | Інші запити падають з помилкою оновлення версії (0 rows updated). |
| **Ризик Deadlock** | **Високий** (при неправильному порядку блокувань). | **Відсутній** на рівні блокування рядків. |

---

### 🎯 Критерії вибору

#### Коли обирати Песимістичне блокування (`SELECT FOR UPDATE`):
1. **Висока конкуренція за ресурси (High Contention):**
   - Розпродаж гарячого товару на складі («Чорна п'ятниця», останні 5 айфонів на 10 000 покупців).
   - Бронювання місць у літаку / квитків на концерт.
   - Списання коштів з банківського рахунку.
2. **Висока вартість конфлікту:**
   - Якщо повторна спроба (retry) коштує дорого (наприклад, вимагає важких обчислень чи повторного походу до зовнішніх API).
3. **Короткі транзакції в межах одного бекенду:**
   - Транзакція відкривається, блокує рядок, оновлює і закомічується за кілька мілісекунд.

#### Коли обирати Оптимістичне блокування (`version` / `updatedAt`):
1. **Низька конкуренція за ресурс (Low Contention):**
   - 99% запитів — читання, і лише 1% — запис.
   - Редагування профілю користувача, оновлення опису товару менеджером.
2. **Довгі користувацькі операції (User Think Time / Long Business Transactions):**
   - Користувач відкриває форму редагування статті в браузері і пише текст 20 хвилин. **Категорично заборонено** тримати песимістичне блокування в БД протягом 20 хвилин, бо це вичерпає пул з'єднань СУБД.
   - Оптимістичне блокування запам'ятовує версію на момент відкриття сторінки, а при кліку на "Зберегти" перевіряє, чи не перезаписав колега цю статтю раніше.
3. **Мікросервісна архітектура без довгих розподілених транзакцій.**

## 4. Deadlock: Що таке взаємне блокування транзакцій у базі даних, чому воно виникає і як його попередити на рівні проєктування коду?

### 📌 Що таке Deadlock?

**Deadlock (Взаємне блокування / глухий кут)** — це ситуація в багатозадачній системі, коли дві або більше транзакції взаємно блокують одна одну, очікуючи на звільнення ресурсів, які тримає інша сторона. Жодна з транзакцій не може продовжити виконання самостійно.

```
Транзакція A: [Захопила Товар 1] ─── намагається захопити ───► [Товар 2] (Зайнято B!)
      ▲                                                              │
      │                                                              ▼
[Товар 1] (Зайнято A!) ◄─── намагається захопити ─── [Захопила Товар 2] : Транзакція B
```

#### Хронологічний приклад:
1. **Транзакція A:** `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;` (захопила Рахунок 1).
2. **Транзакція B:** `SELECT * FROM accounts WHERE id = 2 FOR UPDATE;` (захопила Рахунок 2).
3. **Транзакція A:** `UPDATE accounts SET balance = balance + 10 WHERE id = 2;` ➔ **Чекає на звільнення Рахунку 2.**
4. **Транзакція B:** `UPDATE accounts SET balance = balance + 10 WHERE id = 1;` ➔ **Чекає на звільнення Рахунку 1.**
5. **Цикл замкнувся!**

---

### 🔍 Як СУБД реагує на Deadlock?

База даних не зависає назавжди. У PostgreSQL працює спеціальний фоновий потік (**Deadlock Detector**):
1. СУБД будує орієнтований граф очікувань (**Wait-For Graph**), де вузли — це транзакції, а ребра — очікування на блокування.
2. Якщо транзакція заблокована довше, ніж параметр `deadlock_timeout` (за замовчуванням 1 секунда), СУБД запускає пошук циклів у графі.
3. При знаходженні циклу база обирає одну з транзакцій як **«жертву» (victim)**, примусово перериває її та відкочує:
   ```
   ERROR: deadlock detected
   DETAIL: Process 14023 waits for ShareLock on transaction 84521; blocked by process 14024.
   Process 14024 waits for ExclusiveLock on tuple (0, 1) of relation "accounts"; blocked by process 14023.
   ```
4. Інша транзакція успішно продовжує роботу і закомічується.

### 🛡️ Як попередити Deadlock на рівні проєктування коду

#### 1. Строгий порядок блокувань (Resource Ordering) — Головне правило!
Ресурси завжди повинні блокуватися в **одному й тому самому глобальному порядку** (наприклад, за зростанням ID).
- Якщо треба переказати гроші між акаунтами 42 та 15:
  ```typescript
  // ❌ ПОГАНО: порядок залежить від того, хто відправник
  lock(fromAccount);
  lock(toAccount);

  // ✅ ПРАВИЛЬНО: завжди блокуємо за зростанням ID
  const firstId = Math.min(fromId, toId);
  const secondId = Math.max(fromId, toId);

  await tx.$queryRaw`SELECT * FROM accounts WHERE id = ${firstId} FOR UPDATE`;
  await tx.$queryRaw`SELECT * FROM accounts WHERE id = ${secondId} FOR UPDATE`;
  ```
  Коли всі клієнти блокують ресурси в однаковому порядку (15 ➔ 42), циклічне очікування математично неможливе!

#### 2. Мінімізація часу транзакцій (Short Transactions)
- **Ніколи не робити довгих мережевих викликів всередині SQL-транзакції!** Запити до платіжних систем (Stripe), надсилання email або важка обробка файлів повинні бути за межами транзакції.
- Транзакція повинна лише відкритися, виконати швидкі SQL-запити та миттєво викликати `COMMIT`.

#### 3. Встановлення таймаутів блокування (`lock_timeout`)
Щоб запити не висіли в черзі очікування блокування вічно, обмежуйте максимальний час очікування замка на рівні сесії:
```sql
SET lock_timeout = '2s';
```
Якщо рядок зайнятий понад 2 секунди, запит впаде з помилкою, а не буде нескінченно тримати ресурси пулу.

#### 4. Retry Mechanism з випадковою затримкою (Exponential Backoff + Jitter)
Оскільки взаємні блокування в навантажених системах можуть зрідка траплятися попри всі запобіжні заходи, сервісний шар повинен уміти ловити помилку дедлоку (`40P01` у PostgreSQL) та автоматично перезапускати транзакцію з випадковою паузою:
```typescript
async function executeWithRetry<T>(operation: () => Promise<T>, maxRetries = 3): Promise<T> {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await operation();
    } catch (error: any) {
      if (error.code === '40P01' && attempt < maxRetries) {
        // Додаємо випадкову затримку (jitter), щоб транзакції не зіткнулися знову
        const delay = Math.random() * 100 * Math.pow(2, attempt);
        await new Promise((r) => setTimeout(r, delay));
        continue;
      }
      throw error;
    }
  }
  throw new Error('Max retries exceeded');
}
```
