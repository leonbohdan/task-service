### 🛠️ Архітектура рішення та модульна арифметика

#### 1. Чому звичайний масив не підходить ($O(N)$ проти $O(1)$)

У звичайному JavaScript/TypeScript масиві для реалізації черги "першим прийшов — першим пішов" (FIFO) найстаріший елемент вилучається методом `arr.shift()`.
- **Проблема `arr.shift()`:** Інтерпретатор JavaScript (V8) змушений фізично зсунути всі наступні $N - 1$ елементів на одну позицію ліворуч, щоб закрити порожній нульовий індекс.
- **Складність:** **$O(N)$**. При черзі в десятки тисяч подій на секунду це призводить до колосальної деградації CPU та частих зупинок Garbage Collector.

**Магія кільцевого буфера:**
- Пам'ять виділяється **один раз** фіксованого розміру `capacity`.
- Елементи **ніколи не переміщуються** в пам'яті.
- Замість зсуву масиву ми переміщуємо лише два числових індекси-вказівники: `head` (звідки читати) та `tail` (куди писати).
- Усі операції мають суворо гарантований час **$O(1)$** незалежно від розміру буфера.

#### 2. Детальний розбір змінних стану: навіщо потрібна кожна з них

```typescript
export class CircularBuffer<T> {
  private buffer: (T | undefined)[];
  private head = 0; // Вказівник на найстаріший елемент (читання)
  private tail = 0; // Вказівник на наступну вільну позицію (запис)
  private count = 0; // Кількість фактично збережених елементів
  private readonly capacity: number; // Максимальний розмір
```

| Змінна | Тип | Призначення та інженерна необхідність |
| :--- | :--- | :--- |
| `buffer` | `(T \| undefined)[]` | Статичний масив фіксованого розміру `new Array(capacity)`. Зберігає елементи або `undefined` (якщо комірка порожня або була прочитана через `pop`). |
| `head` | `number` | Вказівник на **найстаріший активний елемент**. Саме звідси метод `pop()` або `peek()` зчитує чергове значення. Починається з `0` і рухається по колу. |
| `tail` | `number` | Вказівник на **наступний вільний слот**, куди метод `push()` запише новий елемент. Після запису зміщується на наступний слот по колу. |
| `count` | `number` | **Критично важлива змінна!** Кількість актуальних елементів у буфері. Усуває класичну проблему кільцевих буферів: коли `head === tail`, буфер може бути або *абсолютно порожнім*, або *повністю заповненим*. Змінна `count` робить методи `isEmpty()`, `isFull()` та `size()` тривіальними перевірками за $O(1)$. |
| `capacity` | `number` | Фіксована максимальна місткість буфера, задана в конструкторі. Використовується як дільник у модульній арифметиці `% capacity`. |

#### 3. Модульна арифметика: як формується нескінченне кільце за $O(1)$

Кільцевий рух забезпечується оператором залишку від ділення (модуль):
$$\text{next\_index} = (\text{current\_index} + 1) \pmod{\text{capacity}}$$

**Як це працює на практиці (для `capacity = 3`):**
- $0 + 1 = 1 \pmod 3 = \mathbf{1}$
- $1 + 1 = 2 \pmod 3 = \mathbf{2}$
- $2 + 1 = 3 \pmod 3 = \mathbf{0}$ *(вказівник автоматично стрибає в початок масиву без жодних `if` або зсувів)*

#### 4. Покроковий розбір коду методів

##### А. Запис з витісненням (`push`):
```typescript
public push(item: T): boolean {
  this.buffer[this.tail] = item;
  this.tail = (this.tail + 1) % this.capacity;

  if (this.isFull()) {
    // Режим Overwrite: якщо буфер був повний, ми перезаписали комірку head.
    // Тому head також повинен зробити крок уперед по колу!
    this.head = (this.head + 1) % this.capacity;
  } else {
    this.count++;
  }

  return true;
}
```
1. Нове значення завжди розміщується в слоті `this.tail`.
2. `tail` робить крок вперед за формулою `(tail + 1) % capacity`.
3. Якщо буфер вже був повний (`isFull() === true`), найстаріший елемент під індексом `head` щойно був перезаписаний новим значенням. Відповідно, новим найстарішим стає наступний за ним елемент, тому `head = (head + 1) % capacity`, а лічильник `count` залишається максимальним (`capacity`).
4. Якщо в буфері було вільне місце, просто збільшуємо лічильник `count++`.

##### Б. Читання з вилученням (`pop`):
```typescript
public pop(): T | undefined {
  if (this.isEmpty()) return undefined;

  const item = this.buffer[this.head];
  this.buffer[this.head] = undefined; // Запобігання витоку пам'яті (V8 Garbage Collector)
  this.head = (this.head + 1) % this.capacity;
  this.count--;

  return item;
}
```
- Зчитуємо елемент за `head`.
- Очищуємо комірку (`undefined`), щоб важкі об'єкти могли бути вчасно зібрані Garbage Collector.
- Зсуваємо `head` вперед на 1 крок по колу і зменшуємо `count--`.
- Усі операції — суворе **$O(1)$**.

##### В. Відновлення хронологічного порядку (`toArray`):
Через постійні цикли перезапису найстаріший елемент може бути де завгодно всередині масиву (наприклад, під індексом `2`, тоді як свіжіші — під `0` та `1`).
```typescript
public toArray(): T[] {
  const result: T[] = [];
  for (let i = 0; i < this.count; i++) {
    const index = (this.head + i) % this.capacity;
    result.push(this.buffer[index] as T);
  }
  return result;
}
```
- Коли `i = 0` $\to$ формується індекс `head` (найстаріший елемент).
- Коли `i = count - 1` $\to$ формується індекс найновішого елемента.

### 💡 Чому кільцевий буфер фундаментальний для Apache Kafka?

1. **In-Memory батчинг продюсера:** Бібліотека `kafkajs` (або офіційний Java-клієнт) не відправляє повідомлення на брокер по одному. Вони акумулюються у внутрішніх кільцевих буферах пам'яті за партиціями до досягнення розміру батчу (`batch.size`) або таймауту (`linger.ms`).
2. **Backpressure та обмеження RAM:** Кільцевий буфер має жорстко обмежену місткість, що запобігає переповненню оперативної пам'яті процесу (Out of Memory) під час тимчасових мережевих затримок або збоїв зв'язку з брокером Kafka.
3. **Висока продуктивність (LMAX Disruptor):** Робота з фіксованими масивами без переалокацій пам'яті дозволяє процесору максимально ефективно кешувати дані в L1/L2/L3 кешах CPU (Cache Locality), що є основою архітектури надшвидких систем стрімінгу.

## 🏗️ Архітектурний огляд: Завдання 2 та 3 (Apache Kafka у KRaft режимі, Partition Key та Consumer Groups)

### 1. Еволюція Kafka: KRaft (Kafka Raft Metadata Mode) проти ZooKeeper

Історично Apache Kafka покладалася на зовнішній ансамбль **Apache ZooKeeper** для координації брокерів, вибору лідера контролера та збереження метаданих топіків і партицій.

```
Класична архітектура (до Kafka 2.8/3.x):
[Producers / Consumers] ---> [Kafka Brokers] <====== Sync ======> [ZooKeeper Ensemble]
                                                                  (Подвійний оверхед на консенсус)

Сучасна архітектура KRaft (Kafka 3.3+ GA):
[Producers / Consumers] ---> [Kafka Brokers (внутрішній Raft Quorum @metadata topic)]
```

#### Чому індустрія перейшла на KRaft:
1. **Ліквідація зовнішньої залежності:** Не потрібно окремо піднімати, моніторити, бекапити та підтримувати JVM-процеси ZooKeeper.
2. **Миттєве відновлення контролера (Sub-second Failover):** У ZooKeeper при зміні лідера-контролера новий контролер мав повністю вичитати всі метадані з ZK у свою пам'ять (що при мільйонах партицій займало хвилини "заморозки" кластера). У KRaft усі контролери постійно реплікують внутрішній топік `@metadata` через протокол Raft, тому при падінні активного контролера резервний стає активним практично миттєво.
3. **Масштабованість метаданих:** Підтримка мільйонів партицій у кластері без деградації синхронізації.

---

### 2. Гарантія суворого порядку за Partition Key (Murmur2)

У розподіленій системі Kafka топік розділений на кілька незалежних партицій. Кожна партиція є строгим незмінним впорядкованим журналом (Append-Only Commit Log).

```
Topic: order.status-changed (3 Partitions)

Partition 0: [offset 0: order-101 (CREATED)] -> [offset 1: order-101 (PAID)] -> [offset 2: order-101 (SHIPPED)]
Partition 1: [offset 0: order-202 (CREATED)] -> [offset 1: order-202 (CANCELLED)]
Partition 2: [offset 0: order-303 (CREATED)] -> [offset 1: order-303 (PAID)]
```

#### Як це працює в коді:
Коли `OrdersService` викликає:
```typescript
this.kafkaClient.emit('order.status-changed', {
  key: orderId, // КРИТИЧНО!
  value: { orderId, status, timestamp },
});
```
Продюсер обчислює номер партиції за алгоритмом:
$$\text{Partition} = |\text{MurmurHash2}(\text{key})| \pmod{\text{Total Partitions}}$$

**Результат:**
- Усі події замовлення `order-101` (`CREATED` $\to$ `PAID` $\to$ `SHIPPED`) гарантовано потраплять в одну й ту саму партицію (наприклад, Partition 0).
- Всередині однієї партиції Kafka гарантує суворий порядок запису і читання (за зростанням offset).

### 3. Топологія Consumer Groups та балансування споживачів

Consumer Group (група споживачів) дозволяє горизонтально масштабувати обробку подій за патерном Competing Consumers:

- **Правило 1 до 1:** Кожна партиція в топіку в конкретний момент часу читається **рівно одним** споживачем всередині конкретної Consumer Group.
- **Один споживач** може читати декілька партицій одночасно.
- **Кількість партицій = Максимальний ліміт паралелізму:**
  - Якщо топік має 3 партиції, а в групі 3 воркери $\to$ кожен воркер читає рівно 1 партицію (ідеальний баланс).
  - Якщо в групі 5 воркерів $\to$ 3 воркери читають по 1 партиції, а 2 воркери простоюють (Idle/Standby), оскільки партицію не можна розділити між споживачами однієї групи.

### 1. Kafka (Pull-модель) проти RabbitMQ (Push-модель)

#### Питання:
*Чому в Kafka споживач сам опитує брокер (`poll()`), а в RabbitMQ брокер виштовхує повідомлення в сокет споживача? Які переваги це дає Kafka при колосальних обсягах даних (High Throughput) та пакетній обробці (Batching)?*

#### Відповідь:

#### Порівняння моделей доставки:

| Характеристика | RabbitMQ (Push-модель) | Apache Kafka (Pull-модель) |
| :--- | :--- | :--- |
| **Ініціатор передачі** | **Брокер**: самостійно виштовхує повідомлення через TCP-з'єднання споживачу. | **Споживач**: сам надсилає запит на брокер за новою порцією даних (`poll()`). |
| **Управління навантаженням** | Потребує механізму обмеження (`basic.qos / prefetch`), інакше брокер переповнить пам'ять воркера. | Природний **Backpressure**: споживач запитує дані лише тоді, коли має вільні ресурси. |
| **Пакетна обробка (Batching)** | Повідомлення здебільшого обробляються поштучно (одиничні ack/nack). | Нативна пакетна доставка: за один запит вичитуються пачки по сотні чи тисячі записів. |
| **Навантаження на стан брокера** | Брокер тримає в RAM стан кожного споживача та кожного повідомлення (unacked, redelivered). | Брокер stateless щодо обробки: він зберігає лише кінцевий числовий зсув (**offset**). |
| **Пропускна здатність** | Десятки тисяч повідомлень на секунду ($10^4$ msg/sec). | Мільйони подій на секунду ($10^6$ msg/sec). |

#### Переваги Pull-моделі для High-Throughput систем:
1. **Ідеальний контроль Backpressure (Захист від перевантаження):**
   - У Push-системі, якщо на продюсері стався сплеск трафіку (Black Friday), брокер почне агресивно пушити події у воркери. Якщо воркер не встигає писати в базу даних, його пам'ять переповнюється, і процес падає через OOM (Out of Memory).
   - У Pull-системі споживач диктує темп: якщо база даних сповільнилася, воркер просто повільніше викликає наступний `poll()`. Дані безпечно накопичуються в Kafka на диску, не ламаючи сервіси-споживачі.
2. **Ефективний батчинг (Batching) та Zero-Copy Transfer:**
   - Споживач може вказати: `fetch.min.bytes = 1048576` (поверни мені дані, тільки якщо накопичився хоча б 1 МБ) або зачекай `fetch.max.wait.ms = 500`.
   - Це дозволяє передавати дані великими неперервними блоками з диску прямо в мережевий сокет за допомогою системного виклику Linux `sendfile()` (**Zero-Copy Architecture**), минаючи копіювання даних у користувацький простір пам'яті (User Space).
3. **Оптимізація запису в цільові сховища:**
   - Отримавши батч із 500 записів за один `poll()`, споживач може виконати один `bulkWrite()` у MongoDB або `INSERT ... VALUES (...), (...)` у PostgreSQL замість 500 окремих мережевих транзакцій.

### 2. Збереження даних (Retention) проти видалення після ACK

#### Питання:
*У RabbitMQ повідомлення після `ack` видаляється з черги. У Kafka повідомлення зберігається в лозі днями або тижнями (`log.retention.hours`). Які архітектурні можливості це відкриває (Replaying events, підключення нових сервісів до історичних даних)?*

#### Відповідь:

У класичних чергах повідомлень (RabbitMQ, SQS) черга розглядається як тимчасовий транзитний буфер: повідомлення надійшло $\to$ обробилося $\to$ підтвердилося (`ack`) $\to$ **безповоротно видалилося**.

У Kafka топік — це **розподілений незмінний журнал фіксації (Append-Only Distributed Commit Log)**. Дані зберігаються на диску незалежно від того, скільки споживачів їх прочитало, протягом періоду `log.retention.hours` (наприклад, 7 днів) або доки не перевищено `log.retention.bytes`.

```
RabbitMQ:    [ Msg 1 ] -> [ Msg 2 ] -> [ Споживач ] ---> (ACK) ---> [ Знищено ]

Kafka:       Partition Log: [0] -> [1] -> [2] -> [3] -> [4] -> [5] (Зберігається 7 днів)
                              ↑                    ↑
                       Consumer Group A     Consumer Group B
                         (offset = 1)         (offset = 4)
```

#### Нові архітектурні можливості:

1. **Replaying Events (Перепрогравання подій / Time Travel):**
   - **Сценарій:** У коді сервісу виставлення рахунків (`billing-service`) виявили помилку в округленні податку, яка спотворювала розрахунки протягом останніх 3 днів.
   - **Вирішення в Kafka:** Ми виправляємо баг у коді, деплоїмо сервіс, і скидаємо офсет групи назад на 3 дні:
     ```bash
     kafka-consumer-groups --bootstrap-server localhost:9092 --group billing-group \
       --reset-offsets --to-datetime 2026-09-11T00:00:00.000 --execute --topic order.status-changed
     ```
   - Сервіс перечитує всі події за останні 3 дні та відновлює коректні розрахунки. У RabbitMQ це було б неможливо, оскільки повідомлення вже давно видалені.

2. **Підключення нових споживачів до історичних даних (Decoupled Evolution):**
   - **Сценарій:** Через пів року після запуску інтернет-магазину бізнес вирішує створити новий мікросервіс рекомендацій та машинного навчання (`recommendation-service`).
   - Новий сервіс реєструється з новою унікальною `groupId: 'ml-recommender-group'` та налаштуванням `auto.offset.reset: earliest`.
   - Він вичитує всю доступну історію замовлень від самого початку топіка, самостійно навчає свої моделі та будує власну аналітичну БД, **жодним чином не навантажуючи робочу базу даних PostgreSQL `order-service`**.

3. **Event Sourcing та CQRS:**
   - Топік Kafka може виступати єдиним непорушним джерелом правди (Single Source of Truth) про всі зміни стану бізнес-сутностей.
   - Будь-які реляційні бази даних, Elasticsearch-індекси або Redis-кеші стають вторинними проекціями (Read Models), які можна будь-коли повністю перегенерувати з нуля шляхом перечитування логу Kafka.

### 3. Гарантія порядку (Ordering Guarantees)

#### Питання:
*Чому Kafka не гарантує глобальний порядок повідомлень по всьому топіку, якщо в ньому більше однієї партиції? Як гарантувати сувору черговість подій для конкретного користувача чи замовлення?*

#### Відповідь:

#### 1. Чому немає глобального порядку:
- У Kafka фундаментальною одиницею паралелізму та фізичного зберігання є **партиція**, а не топік.
- Кожна партиція — це окремий лог-файл із власною незалежною нумерацією зсувів (offsets: 0, 1, 2...).
- Якщо топік має 3 партиції, подія А може записатися в партицію 0 з offset 15, а подія Б — в партицію 1 з offset 2.
- Споживачі всередині Consumer Group читають різні партиції **паралельно та незалежно**. Мережеві затримки, різна швидкість обробки процесорів або підвисання воркерів призводять до того, що подія Б може бути оброблена на 10 мілісекунд раніше за подію А.
- **Єдиний спосіб отримати абсолютно строгий глобальний порядок для всього топіка** — це створити топік із **рівно 1 партицією**. Проте це повністю знищує горизонтальне масштабування: такий топік зможе обробляти лише один споживач одночасно.

#### 2. Рішення індустрії: Порядок на рівні сутності через Partition Key
Для більшості бізнес-систем глобальний порядок подій між різними непов'язаними користувачами не має значення. Критично важливим є **локальний порядок для кожної окремої сутності**:
- Події користувача $A$ повинні йти суворо: `UserRegistered` $\to$ `EmailVerified` $\to$ `AccountUpgraded`.
- Події замовлення №101: `OrderCreated` $\to$ `OrderPaid` $\to$ `OrderShipped`.

**Як це гарантується:**
1. **Передача ключа:** При публікації обов'язково вказується бізнес-ідентифікатор:
   ```typescript
   this.kafkaClient.emit('order.status-changed', {
     key: orderId, // наприклад, 'order-101'
     value: eventData,
   });
   ```
2. **Алгоритм детермінованого хешування:**
   Продюсер використовує хеш-функцію Murmur2:
   $$\text{Partition} = |\text{Murmur2}(\text{key})| \pmod{\text{Partitions Count}}$$
   Оскільки функція чиста і детермінована, один і той самий `orderId` **завжди обчислюється в один і той самий номер партиції**.
3. **Обробка одним споживачем:**
   Оскільки партиція закріплюється лише за одним споживачем у групі, цей споживач читає події послідовно одну за одною, що на 100% гарантує бізнесовий порядок.

#### 3. Надійність продюсера при ретраях:
Якщо мережевий пакет упав, продюсер може спробувати відправити його повторно. Щоб ретраї не змінили порядок подій у партиції, в сучасних версіях Kafka вмикають:
- `enable.idempotence = true` (увімкнено за замовчуванням з Kafka 3.0).
- `max.in.flight.requests.per.connection <= 5` — брокер використовує внутрішні послідовні номери (Sequence Numbers) для кожного батчу від конкретного Producer ID, запобігаючи перестановці або дублюванню повідомлень при мережевих повторах.

### 4. Rebalance Storm у Consumer Groups

#### Питання:
*Що таке ребалансування (Rebalance) у групі споживачів Kafka? Чому падіння або зависання одного воркера може тимчасово зупинити читання для всіх інших учасників групи ("Stop the World") і як допомагає протокол Cooperative Sticky Assignor?*

#### Відповідь:

#### 1. Що таке Rebalance:
**Ребалансування (Rebalance)** — це автоматичний протокол перерозподілу партицій топіка між активними споживачами всередині однієї Consumer Group.

Він тригериться координатором групи (Group Coordinator — один із брокерів Kafka) у випадках:
- До групи підключився новий інстанс споживача (scale out).
- Один з активних споживачів упав або перестав подавати ознаки життя (crash, OOM, мережевий розрив).
- У топік було додано нові партиції.
- Споживач підписався на новий топік за маскою (regex).

---

#### 2. Проблема Eager Rebalance та ефект "Stop the World":
Історично в Kafka використовувався класичний жадібний протокол — **Eager Rebalance Protocol**.

**Як він працював:**
1. При будь-якій події зміни складу групи координатор наказував **усім** споживачам групи: *"Скинути всі призначені партиції і зупинити читання!"*
2. Відбувався повноцінний **Stop-the-World**: уся група припиняла споживання повідомлень.
3. Усі воркери скидали свої збережені офсети в Kafka.
4. Кожен споживач надсилав координатору запит `JoinGroupRequest`.
5. Лідер споживачів перераховував розподіл партицій і повертав його координатору (`SyncGroupRequest`).
6. Воркери нарешті отримували свої нові партиції та відновлювали читання.

#### Що таке Rebalance Storm (Шторм ребалансувань):
Якщо один із воркерів під час обробки важкого батчу зависає на операції введення/виведення (наприклад, повільний запит у зовнішнє API на 40 секунд), він не встигає викликати наступний `poll()` до вичерпання таймауту `max.poll.interval.ms`.
- Координатор вважає цей воркер "мертвим" і запускає **Rebalance №1** (Stop-the-World для всієї групи).
- Усі здорові воркери зупиняються і перерозподіляють партиції.
- Через 10 секунд завислий воркер нарешті завершує свій запит і шле черговий `poll()`. Координатор каже: *"О, ти повернувся!"* — і запускає **Rebalance №2** (знову Stop-the-World).
- Через постійні зупинки тепер уже інший воркер не вкладається в таймаут $\to$ запускається **Rebalance №3**.
- Система входить у **нескінченний каскадний шторм ребалансувань (Rebalance Storm)**, під час якого затримка споживання (Consumer Lag) зростає до критичних значень, а бізнес-процеси зупиняються.

---

#### 3. Порятунок: Cooperative Sticky Assignor (Incremental Cooperative Rebalance)
Починаючи з Kafka 2.4/3.x, стандартом став кооперативний інкрементальний протокол ребалансування — **Cooperative Sticky Assignor** (`CooperativeStickyAssignor`).

#### Принцип роботи:
Замість тотального відкликання всіх партицій у всіх споживачів, перерозподіл відбувається за принципом **мінімальних необхідних змін**:

1. **Без Stop-the-World:** Ті воркери, чиї партиції не зазнають змін, **продовжують безперервно читати та обробляти дані** без жодної зупинки!
2. **Інкрементальність у два етапи:**
   - **Фаза 1:** Споживачі інформують координатора про поточні партиції. Відкликаються **лише ті конкретні партиції**, які дійсно необхідно перемістити (наприклад, партиції впалого воркера).
   - **Фаза 2:** Відібрані партиції передаються новим власникам, тоді як 80–90% кластера продовжує безперебійну роботу.
3. **Результат:** Час ребалансування скорочується з десятків секунд до лічених мілісекунд, а ризик виникнення Rebalance Storm практично зводиться до нуля.
