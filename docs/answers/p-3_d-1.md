### 🛠️ Архітектура рішення та математика алгоритму

#### 1. Формула Full Jitter

У класичному експоненційному бекофі затримка розраховується детерміновано:
$$t_{\text{backoff}} = \min(\text{maxDelayMs}, \text{baseDelayMs} \times 2^{\text{attempt}})$$

Якщо сотні клієнтів одночасно отримують збій (наприклад, рестарт поди в Kubernetes), усі вони повторюють запити синхронно: рівно через 150мс, потім рівно через 300мс, потім 600мс. Це явище називається **Thundering Herd Problem** (ефект натовпу) або фазова синхронізація, яка добиває відновлюваний сервіс.

Алгоритм **Full Jitter** вибирає випадкову величину в повному діапазоні від $0$ до стелі експоненти:
$$t_{\text{sleep}} = \text{random}(0, \min(\text{maxDelayMs}, \text{baseDelayMs} \times 2^{\text{attempt}}))$$

```
Час (ms)  0         100        200        300        400        500
          |----------|----------|----------|----------|----------|
Клієнт 1: [Збій] ──► delay = 23ms  ──► [Спроба 2] ──► delay = 140ms ──► [OK]
Клієнт 2: [Збій] ────────► delay = 113ms ──► [Спроба 2] ──► delay = 223ms ──► [OK]
Клієнт 3: [Збій] ──► delay = 48ms  ──────► [Спроба 2] ──► delay = 9ms ──► [OK]
          (Запити розмазані в часі, пікове навантаження на сервіс усунуто!)
```

#### 2. Ключові інженерні акценти реалізації

1. **Безпечна перевірка опціонального предиката `shouldRetry`:**
   ```typescript
   if (
     attempt === options.maxRetries ||
     (options.shouldRetry && !options.shouldRetry(error))
   ) {
     throw error;
   }
   ```
   *Важливий нюанс:* Використання виразу `!options.shouldRetry?.(error)` є критичною логічною пасткою, адже якщо `shouldRetry` не переданий (`undefined`), `!undefined` обчислюється як `true`, що призводить до негайного падіння на першій же спробі. Перевірка `(options.shouldRetry && !options.shouldRetry(error))` гарантує, що помилка викидається лише тоді, коли фільтр явно переданий і повернув `false`.

2. **Промісифікація таймера (`sleep`):**
   ```typescript
   const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));
   ```
   Дозволяє асинхронно призупиняти виконання конкретної корутини без блокування головного потоку Node.js Event Loop.

3. **Результати тестування трьох паралельних клієнтів (з логів виконання):**
   ```text
   === Запуск 3 паралельних клієнтів ===
   [Спроба #1 невдала] Експоненційний ліміт: 150ms | Обраний Jitter: 23ms
   [Спроба #1 невдала] Експоненційний ліміт: 150ms | Обраний Jitter: 113ms
   [Спроба #1 невдала] Експоненційний ліміт: 150ms | Обраний Jitter: 48ms
   ...
   ```
   Тест наочно підтвердив: незважаючи на одночасний старт, клієнти отримали індивідуальні паузи (23ms, 48ms, 113ms), завдяки чому наступні спроби розподілилися у часі.

## 🏗️ Архітектурний огляд: Завдання 2 та 3 (Ізоляція мережі та буферизація Redis)

### 1. Синхронний REST проти Асинхронної черги: Cascading Failure

У класичній синхронній архітектурі ланцюжок запитів виглядає так:
$$\text{Client} \xrightarrow{\text{HTTP}} \text{OrderService} \xrightarrow{\text{HTTP}} \text{AnalyticsService} \xrightarrow{\text{HTTP}} \text{NotificationService}$$

#### Наслідки відмови або уповільнення `NotificationService`:
1. **Блокування пулу з'єднань (Connection Starvation):** Node.js утримує відкриті сокети та очікує відповіді. Стек пам'яті вичерпується, затримка (`latency`) зростає пропорційно.
2. **Лавиноподібна відмова (Cascading Failure):** Навіть якщо створення замовлення в PostgreSQL пройшло успішно, падіння необов'язкового сповіщення викидає `500 Internal Server Error`. Клієнт бачить збій і не платить гроші. Бізнес зазнає збитків через другорядну функцію.

### 2. Рішення через асинхронний буфер на Redis (`LPUSH` / `BRPOP`)

Замість синхронного виклику `order-service` миттєво публікує задачу в список Redis:
```typescript
// Producer (order-service)
await redisClient.lpush('queue:notifications', JSON.stringify(taskData));
// Відповідь клієнту: 201 Created за ~5-15мс!
```

Воркер у фоновому режимі вичитує завдання:
```typescript
// Consumer (notification-service)
while (true) {
  const [, payload] = await redisClient.brpop('queue:notifications', 0);
  await handleNotification(JSON.parse(payload));
}
```

#### Ключові переваги патерну:
- **Часова розв'язка (Temporal Decoupling):** Сервіс створення замовлень та сервіс сповіщень більше не залежать один від одного в реальному часі. `NotificationService` може бути взагалі вимкнений на обслуговування — замовлення продовжуватимуть створюватися, а черга в Redis накопичуватиметься.
- **Згладжування піків (Spike Arresting / Load Leveling):** Якщо на Чорну П'ятницю надійде 10 000 замовлень за хвилину, сервіс сповіщень не впаде з `OOM`, а рівномірно вичитуватиме задачі з черги зі своєю стабільною пропускною здатністю.

### 1. Теорема CAP у реальних мікросервісних системах

#### Питання:
*Чому в розподілених мережах неможливо відмовитися від складової Partition Tolerance ($P$)? Між чим насправді змушений обирати архітектор під час мережевого збою ($CP$ vs $AP$) і якою системою за класифікацією CAP є типова e-commerce мережа?*

#### Відповідь:

1. **Неможливість відмови від Partition Tolerance ($P$):**
   - У будь-якій розподіленій системі вузли рознесені фізично (різні контейнери, віртуальні машини, стійки або датацентри) і взаємодіють через мережу.
   - Фізична мережа **завжди ненадійна**: трапляються обриви оптичних ліній, перевантаження комутаторів, втрати пакетів, падіння DNS або паузи Garbage Collection, через які нода тимчасово не відповідає на Heartbeat.
   - Відмовитися від $P$ означало б гарантувати, що мережа **ніколи не дасть збою**, що фізично неможливо. Відтак, $P$ — це не вибір, а невідворотна властивість розподіленого середовища.

2. **Реальний вибір архітектора ($CP$ vs $AP$ під час збою):**
   - Оскільки $P$ є обов'язковим, вибір виникає лише в момент настання мережевого розриву (Network Partition):
     - **$CP$ (Consistency + Partition Tolerance):** Система жертвує доступністю заради строгої узгодженості. Якщо репліка не впевнена, що має найсвіжіші дані, вона повертає клієнту помилку або таймаут (`503 Service Unavailable`), блокуючи операції запису/читання (наприклад, консенсусні алгоритми Raft/Paxos, Zookeeper, etcd).
     - **$AP$ (Availability + Partition Tolerance):** Система жертвує абсолютною синхронною узгодженістю заради безперервної доступності. Будь-який доступний вузол повертає відповідь (навіть якщо дані потенційно застарілі), а синхронізація відкладається на потім за моделлю **Eventual Consistency** (наприклад, Amazon DynamoDB, Apache Cassandra, Couchbase).

3. **Класифікація типової e-commerce мережі:**
   - Типова e-commerce система є **$AP$-системою з моделлю кінцевої узгодженості (Eventual Consistency)**.
   - *Бізнес-обґрунтування:* Якщо покупець не зможе додати товар у кошик або натиснути кнопку "Оформити замовлення" через тимчасовий мережевий збій між складами чи сервісами, компанія гарантовано втрачає реальні гроші та клієнта.
   - Тому система приймає замовлення ($AP$), а можливі колізії (наприклад, оверселінг товару, коли залишок виявився меншим за фактичний) компенсуються бізнес-процесами: вибаченням клієнту, нарахуванням бонусних балів, дозамовленням у постачальника або скасуванням через компенсуючу транзакцію в Saga.
   - *Виняток:* Окремі підсистеми (процесинг платежів, списання реального балансу з гаманця) можуть проєктуватися як суворо узгоджені $CP$-острівці всередині загалом $AP$-системи.

### 2. Антипатерн "Розподілений моноліт" (Distributed Monolith)

#### Питання:
*За якими ознаками архітектуру з кількома мікросервісами можна діагностувати як "розподілений моноліт"? Чому синхронні виклики через REST/HTTP між сервісами часто призводять до найгіршого з обох світів (складність мікросервісів + жорстка зв'язаність моноліту)?*

#### Відповідь:

1. **Діагностичні ознаки "Розподіленого моноліту":**
   - **Спільна база даних (Shared Database):** Кілька мікросервісів напряму читають та пишуть у спільні таблиці однієї й тієї ж реляційної БД, минаючи публічні API один одного. Зміна структури однієї таблиці ламає роботу суміжних сервісів.
   - **Координовані релізи (Lockstep Deployments):** Неможливо задеплоїти нову версію одного сервісу без одночасного оновлення ще трьох-чотирьох інших. Відсутня зворотна сумісність контрактів.
   - **Ланцюжки синхронних викликів (Temporal Coupling):** Для обробки одного вхідного запиту сервіс $A$ робить синхронний HTTP-виклик у $B$, $B$ викликає $C$, а $C$ викликає $D$.
   - **Спільні внутрішні бібліотеки з бізнес-логікою:** Зміна DTO або бізнес-правила в shared-пакеті змушує перекомпілювати та редеплоїти абсолютно всі мікросервіси.

2. **Чому синхронний REST/HTTP веде до найгіршого з обох світів:**
   - **Множення ймовірності відмови (Availability Multiplication):** Якщо кожен із сервісів у ланцюжку $A \to B \to C \to D$ має SLA доступності $99.9\%$, сумарна доступність операції становить:
     $$0.999 \times 0.999 \times 0.999 \times 0.999 \approx 99.6\%$$
     Падіння останнього сервісу миттєво обвалює весь ланцюг.
   - **Кумулятивна затримка (Latency Accumulation):** Загальний час очікування відповіді клієнтом є сумою затримок усіх сервісів плюс витрати на сериалізацію/десериалізацію JSON та мережеві RTT.
   - **Виснаження ресурсів (Thread/Socket Pool Exhaustion):** Кожен заблокований синхронний запит утримує сокет і потік пам'яті. Уповільнення одного сервісу викликає лавину блокувань на всіх попередніх рівнях.
   - **Висновки:** Команда отримує всі накладні витрати мікросервісів (складний DevOps, розподілений моніторинг, складна діагностика, мережеві оверхеди), але не отримує жодної їхньої переваги (незалежний деплой, ізольоване масштабування, висока стійкість до відмов).

### 3. Розподілені транзакції: Two-Phase Commit (2PC) проти Saga

#### Питання:
*Чому класичний протокол двофазної фіксації (2PC) вважається антипатерном у масштабованих мікросервісах (блокування ресурсів, координатор як єдина точка відмови)? Як патерн Saga вирішує проблему узгодженості через локальні транзакції та компенсуючі дії (Compensating Transactions)?*

#### Відповідь:

1. **Чому Two-Phase Commit (2PC) є антипатерном у мікросервісах:**
   - **Механіка 2PC:** Протокол складається з двох фаз:
     1. *Фаза голосування (Prepare):* Координатор запитує всіх учасників, чи готові вони зафіксувати транзакцію. Усі бази даних захоплюють ексклюзивні блокування (locks) на відповідні рядки таблиць і тримають їх.
     2. *Фаза фіксації (Commit):* Якщо всі відповіли "Так", координатор надсилає команду на остаточний комміт.
   - **Блокування ресурсів і катастрофічна деградація Latency:** Поки транзакція не завершена, рядки в усіх базах даних заблоковані. Будь-які паралельні запити до цих записів стають у чергу. Мережева затримка між датацентрами робить час утримання блокувань величезним.
   - **Координатор як єдина точка відмови (Single Point of Failure):** Якщо координатор падає після фази Prepare, усі учасники залишаються в невизначеному стані (**in-doubt state**), утримуючи блокування до відновлення координатора.
   - **Порушення автономії сервісів:** 2PC вимагає від СУБД підтримки глобальних XA-транзакцій, що неприйнятно для більшості NoSQL баз, черг повідомлень та сучасних cloud-native сховищ.

2. **Як патерн Saga розв'язує проблему:**
   - **Локальні ACID-транзакції:** Замість однієї глобальної транзакції Сага розбиває бізнес-процес на послідовність незалежних локальних транзакцій $T_1, T_2, \dots, T_n$. Кожен мікросервіс фіксує зміни у власній базі даних атомарно та негайно відпускає локальні блокування.
   - **Компенсуючі транзакції (Compensating Transactions):** Якщо на кроці $T_k$ виникає помилка (наприклад, на складі закінчився товар або банк відхилив транзакцію), Сага запускає ланцюжок зворотних дій у зворотному порядку: $C_{k-1}, \dots, C_1$.
   - **Семантичне скасування замість фізичного відкату:** Компенсація — це не `ROLLBACK` у реляційній базі, а нова явна бізнес-дія, що нейтралізує ефект попередньої (наприклад: дія — "заблокувати 100 грн на картці", компенсація — "повернути 100 грн на картку"; дія — "зарезервувати товар", компенсація — "зняти резерв").
   - **Модель узгодженості:** Сага переводить систему з моделі суворої синхронної узгодженості (ACID) у площину кінцевої узгодженості (BASE — Basically Available, Soft state, Eventual consistency).

### 4. Saga Orchestration vs Saga Choreography

#### Питання:
*У чому полягає фундаментальна різниця між оркестрацією (наявність центрального керуючого сервісу/оркестратора) та хореографією (сервіси слухають події один одного) у патерні Saga? Які переваги та ризики кожного підходу для високонавантаженого бізнесу?*

#### Відповідь:

```
ХОРЕОГРАФІЯ (Event-Driven / Децентралізована)
  OrderService ──(OrderCreated)──► Event Broker ──► PaymentService
                                        │
  InventoryService ◄──(PaymentSuccess)──┘

ОРКЕСТРАЦІЯ (Command-Driven / Централізована)
                  ┌──────────────────────┐
                  │   OrderOrchestrator  │
                  └───────┬───────┬──────┘
             Command 1    │       │   Command 2
         "Authorize"      │       │   "ReserveItems"
                          ▼       ▼
                    PaymentSvc  InventorySvc
```

#### Порівняльна таблиця підходів:

| Критерій | Хореографія (Choreography) | Оркестрація (Orchestration) |
| :--- | :--- | :--- |
| **Принцип керування** | Децентралізований: сервіси реагують на події та публікують нові події в брокер. | Централізований: виділений сервіс-оркестратор надсилає точкові команди іншим сервісам. |
| **Зв'язність (Coupling)** | Слабка (Loose coupling) на рівні мережі; сервіси знають лише про контракти подій. | Сервіси не знають про сусідів, але оркестратор знає про інтерфейси та команди всіх учасників. |
| **Складність розуміння** | Висока при >4-5 кроках: бізнес-потік розмазаний між сервісами ("хто за чим іде"). | Низька: весь алгоритм, стани та переходи знаходяться в одному кодовому файлі/State Machine. |
| **Компенсації** | Складні: кожен сервіс повинен знати, яку компенсацію викликати на певну подію збою. | Прості: оркестратор чітко знає поточний крок і послідовно викликає компенсуючі команди. |
| **Моніторинг і трейсинг** | Потребує наскрізного Distributed Tracing (OpenTelemetry, Correlation IDs). | Вбудований: стан бізнес-процесу зберігається в БД оркестратора (наприклад, Temporal, Camunda). |

#### Переваги та ризики для високонавантаженого бізнесу:

1. **Saga Choreography:**
   - **Переваги:** Максимальна пропускна здатність і мінімальна затримка, оскільки повідомлення проходять безпосередньо через брокер повідомлень (Kafka/RabbitMQ) без додаткового посередника; відсутність єдиної точки відмови (SPOF).
   - **Ризики:** 
     - "Спагеті-архітектура" подій (Event Spaghetti) та ризик циклічних залежностей (сервіс $A$ слухає $B$, який слухає $C$, що реагує на $A$).
     - Надзвичайно складна діагностика аварійних ситуацій: важко зрозуміти, на якому саме етапі зависло замовлення клієнта.
   - **Коли застосовувати:** Прості ланцюжки з 2–4 кроків (наприклад, реєстрація користувача $\to$ створення профілю $\to$ відправка вітального листа).

2. **Saga Orchestration:**
   - **Переваги:** 
     - Абсолютна прозорість бізнес-логіки: процес створення замовлення повністю описаний як скінченний автомат (State Machine).
     - Легке внесення змін: щоб додати новий крок (наприклад, перевірку на шахрайство через Anti-Fraud Service), достатньо змінити код оркестратора, не модифікуючи інші сервіси.
     - Безпечне відновлення після збоїв: оркестратор зберігає історію переходів і може повторити крок після рестарту.
   - **Ризики:**
     - Ризик перетворення оркестратора на "божественний об'єкт" (God Object), де концентрується вся логіка, а решта мікросервісів перетворюються на пасивні анемічні CRUD-виконавці.
     - Додатковий мережевий хоп (RTT) через необхідність звернення до оркестратора на кожному кроці.
   - **Коли застосовувати:** Складні, критично важливі для бізнесу розподілені операції з багатьма учасниками, перевірками та розгалуженими сценаріями компенсацій (наприклад, бронювання подорожі: авіаквиток + готель + оренда авто + страховка).
