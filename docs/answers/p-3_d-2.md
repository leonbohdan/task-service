### 🛠️ Архітектура рішення та математика алгоритму

#### 1. Представлення бінарного дерева в масиві

Бінарна купа — це повне бінарне дерево (Complete Binary Tree), яке компактно зберігається у вигляді звичайного масиву `QueueNode<T>[]` без потреби у виділенні додаткових об'єктів-вказівників на дочірні вузли.

Для будь-якого елемента з індексом $i$:
- **Батьківський вузол (Parent):** $\lfloor (i - 1) / 2 \rfloor$
- **Лівий нащадок (Left Child):** $2i + 1$
- **Правий нащадок (Right Child):** $2i + 2$

```
Деревоподібна структура (Min-Heap):         Масив heap:
            [ 1 ] (idx 0)                     Індекси: [ 0,  1,  2,  3,  4 ]
           /     \                            Значення: [ 1,  2, 10, 15, 20 ]
      [ 2 ]       [ 10 ] (idx 2)
      (idx 1)      
      /   \
  [ 15 ]  [ 20 ]
 (idx 3)  (idx 4)
```

#### 2. Інваріант Min-Heap

Для кожного вузла $i$ (окрім кореня) значення пріоритету батька завжди менше або дорівнює пріоритету нащадка:
$$\text{heap}[\text{parent}(i)].\text{priority} \le \text{heap}[i].\text{priority}$$
У контексті пріоритетної черги **менше числове значення означає вищий пріоритет** (наприклад, пріоритет `1` обробляється раніше за `10`).

#### 3. Алгоритмічні операції

1. **Додавання (`enqueue`):**
   - Новий елемент додається у самий кінець масиву (`this.heap.push({ item, priority })`). Це зберігає форму повного бінарного дерева.
   - Викликається метод просіювання вгору `siftUp(index)`: доки елемент менший за свого батька і не досяг кореня (`index > 0`), він міняється місцями (`swap`) з батьківським вузлом.
   - **Складність:** висота дерева становить $\lfloor \log_2 N \rfloor$, отже час роботи — **$O(\log N)$**.

2. **Вилучення найвищого пріоритету (`dequeue`):**
   - Найпріоритетніший елемент завжди гарантовано знаходиться в корені масиву (`this.heap[0]`).
   - Якщо в купі 1 елемент, повертаємо його через `pop()`.
   - Якщо елементів $> 1$:
     1. Зберігаємо значення кореня для повернення.
     2. Вилучаємо *останній* елемент масиву (`this.heap.pop()`) і ставимо його на місце кореня (`this.heap[0] = last`). Це зберігає структуру повного бінарного дерева.
     3. Викликаємо метод просіювання вниз `siftDown(0)`: елемент у корені порівнюється зі своїми нащадками. Серед лівого та правого нащадків обирається вузол із найменшим пріоритетом (`smallest`). Якщо цей нащадок менший за поточний елемент, вони міняються місцями, і спуск продовжується.
   - **Складність:** **$O(\log N)$**.

3. **Перегляд кореня (`peek`), `size` та `isEmpty`:**
   - Читання кореня без видалення виконується за **$O(1)$**: `this.heap[0]?.item`.
   - Розмір та перевірка на порожнечу — **$O(1)$**.

## 🏗️ Архітектурний огляд: Завдання 2 та 3 (RabbitMQ, AMQP 0-9-1 та Dead Letter Queues)

### 1. Топологія протоколу AMQP 0-9-1

На відміну від спрощених черг (наприклад, Redis списків), в протоколі AMQP 0-9-1 клієнт-продюсер **ніколи не надсилає повідомлення напряму в чергу**. Взаємодія розділена на чіткі абстракції:

```
[ Producer ] ──► ( Exchange ) ──[ Binding / Routing Key ]──► [ Queue ] ──► [ Consumer ]
```

1. **Exchange (Обмінник):** Приймає повідомлення від продюсера та на основі його типу і ключа маршрутизації (`routing_key`) вирішує, у які черги дублювати або направляти повідомлення.
2. **Binding (Зв'язок):** Правило зв'язку між обмінником та конкретною чергою.
3. **Queue (Черга):** Буфер у пам'яті (або на диску), де зберігаються повідомлення до моменту вичитування споживачем.

---

### 2. Забезпечення надійності: Durability, Persistence та Manual ACK

Щоб черга повідомлень витримувала аварійні перезавантаження сервера або збої контейнерів, необхідний трирівневий захист:

1. **Durable Queues & Exchanges (`durable: true`):** Метадані черги та обмінника зберігаються на диску broker-а і відновлюються після рестарту RabbitMQ.
2. **Persistent Messages (`deliveryMode: 2`):** Тіло повідомлення скидається брокером на диск (fsync).
3. **Ручне підтвердження обробки (`noAck: false`):**
   - За замовчуванням RabbitMQ може працювати в режимі автоматичного підтвердження (`noAck: true` або `auto-ack`). У цьому режимі повідомлення видаляється з черги в момент відправки по мережі. Якщо споживач впаде (OOM, unhandled exception), повідомлення безповоротно втрачається.
   - З ручним режимом (`noAck: false`) повідомлення залишається в стані `Unacked` доти, доки воркер явно не викличе `channel.ack(originalMsg)`. Якщо сокет воркера обривається, RabbitMQ негайно повертає повідомлення іншим споживачам.

### 3. Архітектура Dead Letter Queue (DLQ)

```
                       [ orders_exchange ]
                                │ (routing_key: "order_created")
                                ▼
                        [ orders_queue ]
                        (x-dead-letter-exchange: "orders.dlx")
                        (x-dead-letter-routing-key: "orders.dead_letter")
                                │
               ┌────────────────┴────────────────┐
          (Success)                         (Failure / Poison)
               │                                 │
        channel.ack()                  channel.nack(requeue: false)
               │                                 │
         [ Оброблено ]                           ▼
                                          [ orders.dlx ]
                                                 │
                                                 ▼
                                     [ orders.dead_letter ]
                                                 │
                                      [ Ручний аудит / Alert ]
```

Коли воркер отримує пошкоджене повідомлення (наприклад, відсутній обов'язковий email або невалідний JSON), повторна спроба обробки є безглуздою. 
Виклик `channel.nack(originalMsg, false, false)` з параметром `requeue: false` наказує брокеру знищити повідомлення з основної черги. Оскільки для черги налаштовано аргументи `x-dead-letter-exchange`, брокер автоматично перенаправляє "мертве" повідомлення у резервну чергу `orders.dead_letter`.

## 🎯 Відповіді на питання для самоперевірки та інтерв'ю

### 1. Push-модель доставки та параметр `prefetch_count` (Backpressure)

#### Питання:
*RabbitMQ використовує Push-модель: він виштовхує всі доступні в черзі повідомлення на підключеного споживача. Чому за відсутності обмеження `prefetch_count` Node.js споживач може впасти з Out-of-Memory (OOM)? Як працює `prefetch(10)` для балансування навантаження?*

#### Відповідь:

1. **Чому виникає Out-of-Memory (OOM) у Node.js:**
   - За замовчуванням протокол AMQP працює за моделлю **Push**: як тільки клієнт реєструє споживача (`basic.consume`), RabbitMQ намагається негайно відправити йому **всі** накопичені в черзі повідомлення на максимальній швидкості мережевого каналу.
   - Якщо в черзі зібралося 100 000 замовлень, брокер виштовхне їх усі в TCP-сокет клієнта.
   - Драйвер Node.js (`amqplib`) приймає ці бінарні чанки, десеріалізує їх у пам'яті V8 Heap та створює об'єкти повідомлень.
   - Якщо обробка одного повідомлення займає 100 мс (запит до БД, генерація PDF, відправка HTTP), швидкість споживання значно нижча за швидкість виштовхування брокером.
   - Пам'ять V8 переповнюється нерозвантаженими промісами, масивами та буферами. Коли розмір купи перевищує ліміт процесу (за замовчуванням ~1.4–2 ГБ у Node.js), збирач сміття (GC) починає панікувати (GC thrashing), зависає Event Loop, і процес падає аварійно:
     ```text
     FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory
     ```

2. **Механіка Backpressure через `prefetch_count` (Basic QoS):**
   - Метод `channel.prefetch(N)` (в AMQP: `basic.qos(prefetch_count = N)`) реалізує класичний механізм **Backpressure** (зворотного тиску).
   - Він задає розмір "ковзного вікна" (sliding window): брокеру дозволено тримати на даному споживачі не більше ніж $N$ повідомлень у стані `Unacknowledged`.
   - **Як це працює на прикладі `prefetch(10)`:**
     1. RabbitMQ відправляє споживачу 10 повідомлень і зупиняє передачу нових.
     2. Споживач обробляє перше повідомлення і викликає `channel.ack(msg1)`.
     3. Лічильник unacked-повідомлень стає 9.
     4. Брокер бачить звільнення слота і виштовхує рівно одне нове повідомлення (11-те), відновлюючи ліміт 10.

3. **Балансування навантаження (Fair Dispatch):**
   - Без `prefetch` RabbitMQ розподіляє повідомлення наперед блоками. Якщо замовлення №1 потребує важкої обробки на 10 секунд, а замовлення №2–10 легкі, перший воркер буде заблокований, тоді як інші простоюватимуть.
   - З `prefetch(1)` або `prefetch(10)` воркери отримують задачі **по мірі свого реального звільнення**. Швидкі інстанси обробляють більше повідомлень, повільні — менше. Це усуває перекоси навантаження (load skew).

### 2. Патерн Competing Consumers (Паралельні обробники)

#### Питання:
*Що відбувається, коли ми запускаємо 5 реплік контейнера `notification-service`, які підключені до однієї черги `orders_queue`? Чи отримають вони однакові повідомлення, і як RabbitMQ розподіляє повідомлення між ними (Round Robin)?*

#### Відповідь:

1. **Чи отримають споживачі однакові повідомлення:**
   - **Ні, вони НЕ отримають однакові повідомлення.**
   - Черга в RabbitMQ реалізує семантику **Point-to-Point** (Точка-Точка) у поєднанні з патерном **Competing Consumers** (Конкуруючі споживачі).
   - Кожне конкретне повідомлення, що потрапило в чергу `orders_queue`, буде доставлено **лише одному** з п'яти споживачів. Після успішного `ack` повідомлення остаточно видаляється з черги.
   - *(Примітка:)* Якщо бізнесу потрібно, щоб повідомлення отримали всі 5 сервісів одночасно (Broadcast/Pub-Sub), кожен сервіс повинен створити **власну окрему чергу**, і обидві черги мають бути прив'язані (bind) до спільного `Fanout` або `Topic` обмінника.

2. **Алгоритм розподілу повідомлень (Round Robin та Fair Dispatch):**
   - За замовчуванням (якщо `prefetch` не налаштовано або він однаковий) RabbitMQ розподіляє вхідні повідомлення за циклічним алгоритмом **Round-Robin**:
     - Повідомлення 1 $\to$ Споживач A
     - Повідомлення 2 $\to$ Споживач B
     - Повідомлення 3 $\to$ Споживач C
     - Повідомлення 4 $\to$ Споживач D
     - Повідомлення 5 $\to$ Споживач E
     - Повідомлення 6 $\to$ Споживач A і так далі.
   - **Поведінка у продакшені з урахуванням `prefetch`:**
     - Якщо у споживачів налаштовано `prefetch(10)`, брокер відступає від сліпого Round-Robin: він перевіряє поточну кількість `unacked` повідомлень на кожному з'єднанні. Якщо Споживач A ще не підтвердив попередні 10 повідомлень, брокер пропустить його і віддасть наступну пачку Споживачам B, C, D або E.
   - **Масштабування:** Завдяки патерну Competing Consumers ми можемо горизонтально масштабувати сервіс сповіщень простим збільшенням реплік у Kubernetes чи Docker Compose (`docker compose up --scale notification-service=5`), автоматично підвищуючи пропускну здатність системи без зміни коду продюсера.

### 3. Poison Messages та ризик нескінченного циклу

#### Питання:
*Що станеться, якщо у блоці `catch` викликати `channel.nack(originalMsg, false, true)` (`requeue: true`) для повідомлення, яке містить битий невалідний JSON? Чому `requeue: false` у поєднанні з DLQ є обов'язковим стандартом?*

#### Відповідь:

1. **Що станеться при `nack(..., requeue: true)` для битого повідомлення:**
   - Таке повідомлення називається **Poison Message** ("отруйне повідомлення") — воно гарантовано викликає збій при будь-якій спробі десеріалізації чи обробки.
   - **Катастрофічний цикл (Infinite Redelivery Loop):**
     1. Споживач отримує бінарні дані з черги.
     2. Викликається `JSON.parse(data)` $\to$ парсер викидає `SyntaxError: Unexpected token in JSON`.
     3. Керування переходить у блок `catch`.
     4. Код викликає `channel.nack(originalMsg, false, true)`.
     5. Прапорець `requeue: true` змушує RabbitMQ повернути це ж повідомлення назад у чергу (зазвичай у саму голову черги).
     6. Брокер миттєво знову надсилає це повідомлення першому вільному споживачу (часто тому самому, щойно звільненому процесу).
     7. Процес повторюється: `receive` $\to$ `throw` $\to$ `nack(requeue)` $\to$ `receive`...
   - **Наслідки для продакшену:**
     - **100% утилізація CPU:** Процесор ядра зайнятий безперервним безнадійним парсингом битого рядка.
     - **Засмічення дисків логами:** Гігабайти стек-трейсів записуються в лог за лічені хвилини.
     - **Блокування валідних завдань (Head-of-Line Blocking):** Якщо це повідомлення зависає на початку черги, а у воркерів стоїть низький `prefetch`, вся черга замовлень зупиняється.

2. **Чому `requeue: false` + DLQ є обов'язковим інженерним стандартом:**
   - Прапорець `requeue: false` наказує брокеру: *"Це повідомлення непридатне для повторної автоматичної обробки, вилучи його з черги"*.
   - Якщо для черги задано Dead Letter Exchange (`x-dead-letter-exchange`), брокер **не знищує** повідомлення назавжди, а автоматично публікує його в карантинну чергу (`orders.dead_letter`).
   - **Переваги стандарту:**
     - **Ізоляція інциденту:** Основна черга продовжує обробляти валідні транзакції інших користувачів без затримок.
     - **Збереження даних для аудиту:** Жодне бізнес-повідомлення не втрачається безслідно.
     - **Можливість виправлення та повторної відправки (Reprocessing):** Інженери розслідують причину збою в DLQ, виправляють баг у коді або виправляють структуру даних, після чого за допомогою плагіна `rabbitmq_shovel` перекидають повідомлення з DLQ назад в робочу чергу на повторну обробку.

### 4. Порівняння обмінників: Direct vs Fanout vs Topic

#### Питання:
*У яких випадках слід обирати `Fanout` exchange, а коли краще підходить `Topic` з масками на кшталт `orders.eu.*` або `audit.#`? Яка ціна обчислювальної складності маршрутизації в кожному з них?*

#### Відповідь:

#### Порівняльна таблиця типів обмінників:

| Тип Exchange | Логіка маршрутизації | Ключ маршрутизації (`routing_key`) | Обчислювальна складність | Типове застосування |
| :--- | :--- | :--- | :--- | :--- |
| **Direct** | Строгий точний збіг (`routing_key === binding_key`). | Конкретний фіксований рядок (наприклад, `order.created`). | **$O(1)$** (хеш-таблиця) | Адресна доставка завдань конкретним чергам. |
| **Fanout** | Ігнорує routing key; копіює повідомлення у **всі** прив'язані черги. | Не використовується (ігнорується брокером). | **$O(1)$** на пошук зв'язків / **$O(M)$** копій | Широкомовне сповіщення (Broadcast, Pub/Sub). |
| **Topic** | Шаблонний збіг за масками зі спецсимволами (`*` та `#`). | Слова, розділені крапками (наприклад, `orders.eu.electronics`). | **$O(K \times \log M)$** (префіксне дерево/Trie) | Сегментована, мультитенантна, географічна фільтрація. |

#### Спецсимволи в Topic Exchange:
- `*` (зірочка) замінює **рівно одне** слово між крапками.
  - Приклад: `orders.eu.*` перехопить `orders.eu.created` та `orders.eu.cancelled`, але **не** перехопить `orders.eu.b2b.created`.
- `#` (решітка) замінює **нуль або більше** слів.
  - Приклад: `audit.#` перехопить `audit`, `audit.user`, `audit.orders.eu.failed` тощо.

#### Коли обирати Fanout:
1. **Широкомовні повідомлення всім підсистемам (Publish/Subscribe):**
   - Подія "Користувач змінив аватар" або "Оновлено курси валют": усім активним мікросервісам потрібно одночасно скинути свій локальний Redis/In-memory кеш.
   - Відсутність фільтрації: кожна черга отримує абсолютно всі повідомлення без винятку.
2. **Максимальна пропускна здатність:** Коли затримка маршрутизації має бути мінімальною (частки мілісекунди), оскільки брокеру не потрібно виконувати жодних строкових порівнянь.

#### Коли обирати Topic:
1. **Географічна та регіональна ізоляція:**
   - Споживач у Франції слухає `orders.eu.fr.*`, німецький склад слухає `orders.eu.de.*`, а глобальний дата-лейк аналітики слухає `orders.#`.
2. **Селективний аудит та моніторинг:**
   - Сервіс сповіщень безпеки цікавлять лише події рівня критичних збоїв: підписка на `*.error` або `security.#`.
3. **Економія ресурсів споживачів:** Замість того, щоб вичитувати мільйони непотрібних подій і викидати їх у коді воркера (фільтрація на стороні клієнта), фільтрація виконується високоефективним брокером ще до відправки по мережі.

#### Ціна обчислювальної складності (Internal Broker Mechanics):
- **Fanout ($O(1)$):** Брокер зберігає простий масив або хеш-сет черг для обмінника. Маршрутизація зводиться до швидкого ітерування по списку сокетів/черг і створення копій покажчиків повідомлень.
- **Direct ($O(1)$):** Брокер використовує звичайну хеш-таблицю (Hash Table Lookup), де ключем є точний рядок `routing_key`. Пошук черги відбувається за константний час.
- **Topic ($O(K \times \log M)$ або Radix Tree Trie):** Для співставлення масок із `*` та `#` RabbitMQ (на базі Erlang/OTP) реалізує спеціальний алгоритм **Trie Pattern Matching** (префіксні дерева станів). Кожне слово ключа маршрутизації розбивається за крапками та звіряється з графом переходів.
  - *Ціна:* При сотнях тисяч повідомлень на секунду та тисячах складних прив'язок Topic Exchange споживає відчутно більше CPU брокера порівняно з Fanout та Direct. Проте цей оверхед повністю виправдовує себе гнучкістю архітектури та економією мережевого трафіку між брокером і воркерами.
