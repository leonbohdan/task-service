### 🛠️ Архітектура рішення: Двоетапний Pipeline

Утиліта `aggregateSales` побудована за принципом конвеєра обробки даних (Data Processing Pipeline), розділеного на дві фази:

```
Вхідні дані (SaleRecord[])
        │
        ▼
┌────────────────────────────────────────────────────────┐
│ Фаза 1: Акумуляція даних (аналог $group у MongoDB)    │
│ - Однопрохідний reduce() за O(N)                       │
│ - Динамічне формування ключа: groupByKeys.join(":")    │
│ - Накопичення сум: totalRevenue, totalUnits, count     │
└────────────────────────────────────────────────────────┘
        │
        ▼
┌────────────────────────────────────────────────────────┐
│ Фаза 2: Фіналізація та проєкція (аналог $project)     │
│ - Прохід по унікальних групах за O(K), де K <= N       │
│ - Безпечний розрахунок averagePricePerUnit             │
│ - Округлення до 2 знаків: Number(val.toFixed(2))       │
└────────────────────────────────────────────────────────┘
        │
        ▼
Результат (AggregationResult)
```

#### Ключові інженерні акценти:

1. **Сувора типізація ключів (`keyof SaleRecord`):**
   Використання типу `(keyof SaleRecord)[]` унеможливлює передачу неіснуючих полів на етапі компіляції:
   ```typescript
   export function aggregateSales(
     records: SaleRecord[],
     groupByKeys: (keyof SaleRecord)[],
   ): AggregationResult
   ```
2. **Динамічний ключ із фолбеком:**
   ```typescript
   const key = groupByKeys.map((k) => record[k]).join(":") || "_total_";
   ```
   Якщо передати порожній масив ключів `[]`, метод не впаде, а агрегує всі записи в єдину загальну групу `"_total_"`.
3. **Відокремлення акумуляції від фіналізації:**
   Розрахунок середнього значення (`averagePricePerUnit`) винесено у другий етап. Це оптимізує навантаження на процесор, оскільки «важке» ділення чисел з рухомою комою та форматування `.toFixed(2)` виконується лише один раз для кожної унікальної групи ($K$ разів), а не на кожному з $N$ записів.
4. **Захист від ділення на нуль (Edge Case):**
   ```typescript
   averagePricePerUnit: totalUnits > 0 ? Number((totalRevenue / totalUnits).toFixed(2)) : 0
   ```
   Запобігає появі значень `Infinity` або `NaN`, якщо в групі немає проданих одиниць.

## 1. Pipeline-модель: Чому порядок операторів у конвеєрі агрегацій MongoDB має вирішальне значення, на відміну від порядку слів у декларативному SQL-запиті?

### 📌 Коротке резюме
* **SQL є декларативною мовою (Declarative):** розробник описує *«Що саме потрібно отримати»*, а внутрішній Cost-Based Optimizer (CBO) реляційної СУБД самостійно вирішує, *«Як це зробити»* (переставляє порядок фільтрації, обирає індекси та алгоритми джойнів).
* **MongoDB Aggregation Pipeline є конвеєром обробки потоку документів (Imperative/Pipes & Filters):** порядок етапів визначає **послідовність трансформації даних**. Кожен етап приймає потік документів від попереднього, трансформує його і передає наступному. Неправильний порядок етапів веде або до зміни бізнес-результату, або до катастрофічного падіння продуктивності.

---

### 🔬 Детальне порівняння: SQL vs MongoDB Pipeline

```
SQL: Декларативний запит                    MongoDB: Потоковий конвеєр (Pipeline)
┌───────────────────────────────┐           ┌─────────────────────────────────────────┐
│ SELECT category, SUM(price)   │           │ db.orders.aggregate([                   │
│ FROM orders                   │           │   { $match: { status: 'COMPLETED' } },  │ ── Stage 1 (Filter)
│ WHERE status = 'COMPLETED'    │ ── CBO ──►│   { $project: { category: 1, price: 1 } },│ ── Stage 2 (Reshape)
│ GROUP BY category             │           │   { $group: { _id: '$category', ... } },│ ── Stage 3 (Aggregate)
│ HAVING SUM(price) > 1000;     │           │   { $sort: { totalRevenue: -1 } }       │ ── Stage 4 (Sort)
└───────────────────────────────┘           │ ])                                      │
  Порядок слів у запиті фіксований          └─────────────────────────────────────────┘
  синтаксисом, але фізичний план               Порядок стадій суворо визначає послідовність
  будує оптимізатор (CBO).                     обробки потоку документів у RAM/диску.
```

#### Чому порядок стадій у MongoDB має вирішальне значення:

1. **Раннє відсікання даних (Early Filtering) та використання індексів:**
   - Якщо стадія `$match` стоїть першою, MongoDB може скористатися B-Tree індексами колекції, швидко відібравши лише 1 000 документів із 10 000 000.
   - Якщо перед `$match` помилково поставити `$group` або `$lookup`, база змушена буде згрупувати чи з'єднати всі 10 мільйонів документів у пам'яті, а вже потім відкинути 99.9% результатів.
2. **Семантична залежність результату (`$sort` + `$limit` vs `$limit` + `$sort`):**
   - `{ $sort: { revenue: -1 } }, { $limit: 5 }` — знаходить **ТОП-5 найприбутковіших** магазинів.
   - `{ $limit: 5 }, { $sort: { revenue: -1 } }` — бере **перші 5 випадкових** магазинів із колекції та сортує між собою лише їх. Результат повністю спотворюється.
3. **Зміна структури документа (Reshaping):**
   - Етап `$project` або `$group` змінює набір полів або замінює `_id`. Якщо наступний етап посилається на поле, яке було вилучено або перейменовано попереднім етапом, поле буде оцінено як `undefined`/`null`, і запит поверне порожні або некоректні дані.

> [!NOTE]
> **Pipeline Optimization:** MongoDB має внутрішній оптимізатор конвеєрів, який намагається виконати оптимізації (наприклад, об'єднати суміжні стадії `$match` або пересунути сумісні проєкції). Проте він не може змінити порядок операцій, якщо це впливає на семантику або якщо між ними знаходяться блокуючі стадії кшталту `$group`.

## 2. Індексація в конвеєрі: За яких умов етап `$match` може використовувати індекси колекції, і що відбудеться, якщо перед ним розмістити `$project` або `$group`?

### 📌 Коротке резюме
* Етап `$match` може використовувати індекси колекції **виключно тоді, коли він розташований на самому початку конвеєра** (першою стадією або одразу після іншого `$match`, з яким об'єднується).
* Якщо перед `$match` розмістити `$group` або `$project`, **доступ до індексів вихідної колекції повністю втрачається**. MongoDB буде змушена виконувати повне сканування згенерованих документів у пам'яті (**Full In-Memory Scan**).

---

### 🔍 Детальний технічний механізм

#### 1. Чому `$project` або `$group` ламають індекси:
B-Tree індекси прив'язані до **фізичних документів у колекції на диску**. 

Коли виконується стадія `$group` або `$project`:
1. Створюється **новий потік тимчасових об'єктів (Ephemerals)** у пам'яті.
2. Ці згенеровані об'єкти більше не є документами вихідної колекції на диску — вони не мають фізичного `RecordId` і не зареєстровані у B-Tree індексах.
3. Коли наступна стадія `$match` намагається відфільтрувати ці об'єкти, вона не має жодного індексу, до якого могла б звернутися. Відбувається лінійне сканування кожного проміжного документа в оперативній пам'яті.

```
[Диск: Колекція з B-Tree індексами]
               │
               ▼
   ┌───────────────────────┐
   │    Стадія 1: $group   │ ──► Генерує синтетичні документи в RAM (зв'язок з B-Tree втрачено!)
   └───────────────────────┘
               │
               ▼
   ┌───────────────────────┐
   │    Стадія 2: $match   │ ──► 💥 COLLSCAN / In-Memory Scan! Індекси недоступні.
   └───────────────────────┘
```

#### 2. Коли `$match` використовує індекс:
1. **Позиція:** Етап `$match` стоїть першим у конвеєрі:
   ```javascript
   db.orders.aggregate([
     { $match: { status: 'COMPLETED', orderedAt: { $gte: startDate } } }, // ✅ Використовує складений індекс { status: 1, orderedAt: -1 }
     { $group: { _id: '$category', total: { $sum: '$totalPrice' } } }
   ]);
   ```
2. **Відповідність предикатів індексам:** Поля у фільтрі повинні задовольняти правилу лівого префікса складеного індексу або покриватися простим індексом.
3. **Compound Pipeline Stage ($match + $sort):** Якщо `$match` і наступний `$sort` стоять на початку, MongoDB може використати один складений індекс як для фільтрації, так і для неблокуючого сортування без завантаження всіх даних у пам'ять.

## 3. Ліміти оперативної пам'яті: Яке системне обмеження RAM має один етап агрегації (100 МБ) за замовчуванням, і як параметр `allowDiskUse: true` впливає на ресурси?

### 📌 Коротке резюме
* **Дефолтне обмеження:** Будь-який окремий етап конвеєра агрегацій у MongoDB має жорсткий ліміт пам'яті в **100 МБ RAM** (для стадій блокуючої акумуляції: `$sort` без індексу, `$group`, `$bucket`). При перевищенні ліміту запит аварійно переривається з помилкою.
* **Параметр `allowDiskUse: true`:** Дозволяє виносити проміжне сортування та акумуляцію у тимчасові файли на диску (`_tmp`), рятуючи запит від падіння, але призводить до суттєвого сповільнення через операції дискового вводу-виводу (Disk I/O).

---

### 🔬 Детальний розбір лімітів та поведінки

#### 1. Чому виникає ліміт 100 МБ?
Більшість стадій конвеєра (наприклад, `$match`, `$project`, `$unwind`) є **потоковими (Streaming)** — вони обробляють документ за документом і відразу виштовхують його далі без накопичення.
Проте стадії на кшталт:
- `$sort` (якщо сортування відбувається не за індексом);
- `$group` (який накопичує всі унікальні ключі та акумулятори);

є **блокуючими (Blocking / Accumulating)**. Вони не можуть видати жодного документа, доки не прочитають і не оброблять увесь набір даних. Щоб захистити сервер від вичерпання пам'яті (OOM — Out Of Memory) через один невдалий користувацький запит, MongoDB обмежує розмір буфера пам'яті для кожної такої стадії рівно в **100 МБ**.

Якщо стадія перевищує ліміт:
```
MongoServerError: PlanExecutor error during aggregation :: caused by :: 
Sort exceeded memory limit of 104857600 bytes, but did not opt in to external sorting.
```

#### 2. Як працює `allowDiskUse: true`:
```typescript
await this.orderModel.aggregate(pipeline).allowDiskUse(true).exec();
```
При активації цього прапорця:
1. Якщо стадія досягає ліміту 100 МБ RAM, MongoDB створює системні тимчасові файли у підкаталозі `_tmp` у каталозі даних `dbPath`.
2. Дані скидаються на диск блоками за допомогою алгоритму зовнішнього сортування/злиття (**External Merge Sort**).
3. Після завершення агрегації всі тимчасові файли автоматично видаляються.

#### 3. Компроміси та вплив на ресурси (Trade-offs):

| Параметр | Виконання у RAM (дефолт) | Використання диску (`allowDiskUse: true`) |
| :--- | :--- | :--- |
| **Швидкість** | Мікросекунди / мілісекунди | Секунди / десятки секунд (у 10-100 разів повільніше) |
| **Вплив на диск** | Відсутній | Сплеск дискового I/O, конкуренція за операції читання/запису (I/O Wait) |
| **Надійність** | Може впасти з помилкою 100 MB Limit | Запит гарантовано добігає кінця |
| **Сфера застосування** | **Real-time OLTP API** (відповіді для вебу/мобілок) | **Нічні Batch Jobs, важка аналітика, експорт звітів** |

> [!WARNING]
> Використання `allowDiskUse: true` для публічних користувацьких REST API вважається антипатерном. Якщо звичайний API-ендпоінт вимагає `allowDiskUse`, це свідчить про архітектурну проблему: відсутність ранньої фільтрації `$match`, відсутність необхідного індексу для `$sort`, або спробу обробити неагреговані Big Data безпосередньо в запиті клієнта.

## 4. `$project` vs `$addFields`: У чому концептуальна різниця між цими двома операторами та коли доцільно використовувати кожен із них?

### 📌 Коротке резюме
* **`$project` (White-listing / Reshaping):** працює за принципом **«білого списку»**. Залишає лише ті поля, які явно вказані, і відсікає всі інші. Призначений для кардинальної зміни форми документа, перейменування полів та відсікання важких даних.
* **`$addFields` (також відомий як `$set` з версії 4.2):** працює за принципом **розширення (Enrichment)**. Зберігає абсолютно всі наявні поля документа, додаючи нові або перезаписуючи значення існуючих.

---

### 📊 Порівняльна таблиця

| Характеристика | `$project` | `$addFields` (`$set`) |
| :--- | :--- | :--- |
| **Поведінка за замовчуванням** | Видаляє всі поля, крім зазначених (та `_id`) | Зберігає **всі** поля, додає лише нові |
| **Використання пам'яті** | Мінімізує обсяг документа в конвеєрі | Обсяг документа зростає |
| **Стійкість до змін схеми** | **Низька:** нові поля в документі автоматично відсікаються | **Висока:** будь-які нові поля залишаються недоторканими |
| **Перейменування полів** | Так: `{ newName: '$oldName' }` | Тільки копіювання: старе поле залишиться, якщо не видалити |
| **Основний сценарій** | Формування фінальної DTO-відповіді, відсікання зайвого | Додавання проміжних обчислюваних метрик |

---

### 🛠️ Практичні сценарії використання

#### Сценарій 1: Коли `$addFields` набагато кращий за `$project`
Уявіть документ `Product` із 25 полями. Вам потрібно просто додати одне обчислюване поле `vatAmount`:

```javascript
// ❌ Погано через $project: доведеться вручну перераховувати всі 25 полів!
{
  $project: {
    sku: 1,
    title: 1,
    description: 1,
    category: 1,
    price: 1,
    // ... ще 20 полів ...
    vatAmount: { $multiply: ['$price', 0.2] }
  }
}

// ✅ Ідеально через $addFields:
{
  $addFields: {
    vatAmount: { $multiply: ['$price', 0.2] }
  }
}
```
Якщо в майбутньому в схему `Product` додадуть поле `barcode`, варіант з `$addFields` продовжить працювати коректно, а `$project` тихо відкине це поле.

#### Сценарій 2: Коли необхідний саме `$project`
1. **Фінальне формування контракту відповіді:**
   ```javascript
   {
     $project: {
       _id: 0,                           // Приховуємо внутрішній ID
       category: '$_id',                 // Перейменовуємо _id на зрозуміле ім'я
       totalRevenue: 1,
       averageCheck: { $round: ['$avgPrice', 2] }
     }
   }
   ```
2. **Оптимізація пам'яті перед важкими стадіями (Projection Pushdown):**
   Якщо документ містить великі поля (наприклад, історію логів `auditLog` чи base64 аватар), їх варто відсікти через `$project` на початку конвеєра, щоб наступні стадії `$group` чи `$sort` не витрачали оперативну пам'ять на перекладання зайвих гігабайтів.
