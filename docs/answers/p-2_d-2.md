### 🛠️ Архітектура рішення: Функціональна деконструкція з `flatMap`

Утиліта `unwind` побудована на базі методу `Array.prototype.flatMap()`, що дозволяє за один прохід розгортати кожен об'єкт у підмасив нових сутностей і автоматично об'єднувати їх у результуючий плаский список.

```
Вхідний масив документів (T[])
              │
              ▼
┌────────────────────────────────────────────────────────┐
│ Ранній вихід (Guard Clause)                            │
│ Якщо !Array.isArray(docs) || docs.length === 0 ──► []   │
└────────────────────────────────────────────────────────┘
              │
              ▼
┌────────────────────────────────────────────────────────┐
│ Обхід через docs.flatMap(doc => ...)                   │
│ Аналіз цільового поля: target = doc[arrayKey]          │
└────────────────────────────────────────────────────────┘
        │                                  │
        ▼                                  ▼
┌───────────────────────────────┐ ┌───────────────────────────────────────┐
│ Сценарій А: Непорожній масив │ │ Сценарій Б: [], null або undefined    │
│ Array.isArray(target) && > 0  │ │                                       │
│                               │ │ 1. preserveNullAndEmptyArrays: true   │
│ target.map(item => ({         │ │    ──► [{ ...doc, [key]: null }]      │
│   ...doc,                     │ │ 2. preserveNullAndEmptyArrays: false  │
│   [arrayKey]: item            │ │    ──► [] (документ відкидається)     │
│ }))                           │ └───────────────────────────────────────┘
└───────────────────────────────┘
              │
              ▼
Фінальний плаский список розгорнутих документів
```

#### Ключові інженерні акценти:

1. **Сувора типізація через `infer` та `Mapped Types`:**
   ```typescript
   export type UnwoundDocument<T, K extends keyof T> = Omit<T, K> & {
     [P in K]: T[K] extends Array<infer Item> ? Item : never;
   };
   ```
   - `Omit<T, K>` видаляє оригінальне поле-масив із типу документа.
   - `T[K] extends Array<infer Item> ? Item : never` витягує точний тип окремого елемента масиву на етапі компіляції.
   - Якщо передано прапорець збереження, результуючий юніон-тип `Array<UnwoundDocument<T, K> | (Omit<T, K> & { [P in K]?: null })>` дозволяє безпечно обробляти значення `null`.

2. **Іммутабельність (Immutability):**
   Жоден вхідний об'єкт не мутується. Створення розгорнутих копій відбувається через Object Spread (`{ ...doc, [arrayKey]: item }`).

3. **Очищення вкладеності (Guard Clauses):**
   Використання ранньої перевірки валідності масиву позбавляє від надлишкової вкладеності блоків `if-else` і гарантує безпечне виконання.

## 🛠️ Довідник ключових операторів MongoDB Aggregation Pipeline: Як вони працюють та коли їх застосовувати

MongoDB Aggregation Pipeline побудований за архітектурним патерном **Pipes & Filters** (Конвеєри та Фільтри). Потік BSON-документів послідовно проходить через незалежні стадії (Stages), де кожна стадія трансформує дані та передає результат наступній.

Нижче наведено детальний огляд усіх ключових операторів конвеєра, їхній синтаксис, принцип роботи та практичні особливості.

---

### 1. Оператори реляційних зв'язків та розгортання масивів

#### 🔹 `$lookup` (Basic Equality Match — Реляційний Left Outer Join)
* **Призначення:** Приєднує документи з іншої колекції (`from`) на основі рівності двох полів: `localField` (з поточної колекції) та `foreignField` (з приєднуваної).
* **Принцип роботи:** Для кожного вхідного документа виконує пошук у цільовій колекції та поміщає всі знайдені документи у вигляді **масиву** в нове поле `as`. Якщо збігів немає — повертає порожній масив `[]`.
* **Синтаксис:**
  ```javascript
  {
    $lookup: {
      from: "customers",        // Цільова колекція
      localField: "customerId", // Поле в поточному документі (Orders)
      foreignField: "_id",      // Поле в колекції Customers
      as: "customerDetails"     // Нове поле-масив для результату
    }
  }
  ```
* **Важлива деталь:** Оскільки `$lookup` завжди повертає масив (навіть для зв'язку 1:1), для отримання плоского об'єкта наступним кроком зазвичай ставлять `$unwind`.

---

#### 🔹 `$lookup` (Correlated Subquery — Вкладений конвеєр з `let` та `pipeline`)
* **Призначення:** Дозволяє виконувати складні підзапити до приєднуваної колекції: застосовувати фільтрацію, проєкцію, сортування, оператори `$in` та складні вирази ще до повернення результату.
* **Принцип роботи:** Через блок `let` оголошуються змінні з полів батьківського документа. У блоці `pipeline` описується незалежний підконвеєр над цільовою колекцією, де доступ до оголошених змінних здійснюється через подвійний знак долара (`$$variable`).
* **Синтаксис:**
  ```javascript
  {
    $lookup: {
      from: "products",
      let: { orderProductIds: "$items.productId" },
      pipeline: [
        {
          $match: {
            $expr: { $in: ["$_id", "$$orderProductIds"] }
          }
        },
        { $project: { title: 1, costPrice: 1, sku: 1 } }
      ],
      as: "matchedProducts"
    }
  }
  ```
* **Перевага:** Суттєво знижує навантаження на мережу та пам'ять, оскільки відсікає зайві поля та документи безпосередньо в момент джоїну.

---

#### 🔹 `$unwind` (Деконструкція та розгортання масивів)
* **Призначення:** Розгортає поле-масив так, що для кожного елемента масиву створюється окрема копія батьківського документа.
* **Принцип роботи:** Документ із масивом з $K$ елементів перетворюється на $K$ окремих документів, де замість масиву записаний один його конкретний елемент.
* **Синтаксис:**
  ```javascript
  // Коротка форма:
  { $unwind: "$items" }

  // Розширена форма з опціями:
  {
    $unwind: {
      path: "$items",
      preserveNullAndEmptyArrays: true, // Зберігати документи з [], null або undefined
      includeArrayIndex: "itemIndex"    // Додати поле з індексом елемента (0, 1, 2...)
    }
  }
  ```
* **Підводний камінь:** Якщо масив містить сотні елементів, виникає **Document Explosion** (множення документів), що може вичерпати 100 МБ оперативної пам'яті конвеєра.

### 2. Оператори фасетної аналітики та сегментації даних

#### 🔹 `$facet` (Багатовимірна аналітика за один прохід)
* **Призначення:** Дозволяє обробити один і той самий потік вхідних документів кількома незалежними підконвеєрами одночасно. Ідеально підходить для побудови комплексних аналітичних дашбордів за один запит до бази.
* **Принцип роботи:** Приймає документи після попередньої фільтрації (`$match`) та паралельно передає їх у зазначені іменовані гілки конвеєра.
* **Синтаксис:**
  ```javascript
  {
    $facet: {
      "kpiSummary": [
        { $group: { _id: null, totalRevenue: { $sum: "$totalPrice" }, count: { $sum: 1 } } }
      ],
      "topProducts": [
        { $unwind: "$items" },
        { $group: { _id: "$items.productId", soldUnits: { $sum: "$items.quantity" } } },
        { $sort: { soldUnits: -1 } },
        { $limit: 5 }
      ],
      "priceBuckets": [
        { $bucket: { groupBy: "$totalPrice", boundaries: [0, 100, 500, 1000], default: "1000+" } }
      ]
    }
  }
  ```
* **Головне обмеження:** Результуючий об'єкт формується як **один BSON-документ**, який суворо обмежений розміром **16 MB**.

---

#### 🔹 `$bucket` (Ручна сегментація за числовими діапазонами / Гістограми)
* **Призначення:** Класифікує вхідні документи за числовими кошиками (діапазонами) на основі заданих меж (`boundaries`).
* **Принцип роботи:** Перевіряє значення виразу `groupBy` за напіввідкритими інтервалами: `[нижня_межа, верхня_межа)` — нижня межа включається, верхня ні. Значення, що не потрапили в жоден інтервал, відправляються в кошик `default`.
* **Синтаксис:**
  ```javascript
  {
    $bucket: {
      groupBy: "$totalPrice",
      boundaries: [0, 100, 500, 1000, 5000], // [0-99.99], [100-499.99], [500-999.99], [1000-4999.99]
      default: "VIP (5000+)",
      output: {
        orderCount: { $sum: 1 },
        totalRevenue: { $sum: "$totalPrice" },
        averageTicket: { $avg: "$totalPrice" }
      }
    }
  }
  ```

---

#### 🔹 `$bucketAuto` (Автоматичне квантування)
* **Призначення:** Автоматично розбиває потік документів на задану кількість кошиків ($N$), намагаючись розподілити документи рівномірно (квантилі).
* **Синтаксис:**
  ```javascript
  {
    $bucketAuto: {
      groupBy: "$totalPrice",
      buckets: 5, // База самостійно порахує оптимальні межі для 5 однакових за кількістю груп
      output: { count: { $sum: 1 } }
    }
  }
  ```

### 3. Фундаментальні стадії фільтрації, трансформації та агрегації

#### 🔹 `$match` (Фільтрація потоку документів)
* **Призначення:** Відбирає лише ті документи, які відповідають зазначеним предикатам.
* **Чому це критично:** Якщо `$match` розміщено на самому початку конвеєра, він працює напряму з B-Tree індексами колекції (`IXSCAN`), відсікаючи мільйони непотрібних документів за мікросекунди.

---

#### 🔹 `$project` vs `$addFields` / `$set` (Трансформація схеми документа)
* **`$project`:** Створює новий документ «з нуля». Усе, що явно не зазначено як `1`, викидається (окрім `_id`, який треба явно вимикати: `_id: 0`).
* **`$addFields` (або `$set`):** Додає нові обчислювані поля або оновлює існуючі, **зберігаючи всі інші поля документа недоторканими**. Це значно зручніше, якщо потрібно збагатити документ без переліку десятків полів.
* **Приклад `$set`:**
  ```javascript
  {
    $set: {
      margin: { $subtract: ["$totalPrice", "$costPrice"] },
      isVipOrder: { $gte: ["$totalPrice", 1000] }
    }
  }
  ```

---

#### 🔹 `$group` (Акумуляція та групування)
* **Призначення:** Групує документи за спільним ключем `_id` та обчислює сумарні метрики.
* **Ключові акумулятори:**
  * `$sum`: Підсумовує числові значення або рахує кількість записів (`{ $sum: 1 }`).
  * `$avg`: Обчислює середнє арифметичне.
  * `$min` / `$max`: Знаходить екстремуми.
  * `$push`: Збирає всі значення поля в масив (з дублікатами).
  * `$addToSet`: Збирає тільки унікальні значення поля в масив.
  * `$first` / `$last`: Бере значення з першого або останнього документа в групі (має сенс після `$sort`).

---

#### 🔹 `$sort`, `$limit`, `$skip` (Впорядкування та пагінація)
* **`$sort`:** Впорядковує потік за полями (1 — за зростанням, -1 — за спаданням). Якщо перед ним немає індексу, сортування відбувається в пам'яті (ліміт 100 МБ).
* **Оптимізація `$sort` + `$limit` (Top-N Coalescence):** Якщо ці два оператори стоять поруч, MongoDB оптимізує сортування: замість сортування всього масиву в пам'яті підтримується B-Tree куча лише на $N$ елементів.

---

### 4. Оператори виразів масивів (Array Expression Operators)

Якщо потрібно обробити масив всередині документа, замість важкої зв'язки `$unwind` + `$group` використовують вбудовані вирази масивів, які працюють in-memory без дублювання документів:

| Оператор | Призначення | Приклад використання |
| :--- | :--- | :--- |
| **`$filter`** | Відбирає елементи масиву за умовою | `{ $filter: { input: "$items", as: "it", cond: { $gte: ["$$it.price", 100] } } }` |
| **`$map`** | Трансформує кожен елемент масиву | `{ $map: { input: "$items", as: "it", in: "$$it.productId" } }` |
| **`$reduce`** | Згортає масив в одне значення | `{ $reduce: { input: "$items", initialValue: 0, in: { $add: ["$$value", "$$this.price"] } } }` |
| **`$size`** | Повертає довжину масиву | `{ $size: "$items" }` |
| **`$in`** | Перевіряє наявність елемента в масиві | `{ $in: ["prod-A", "$items.productId"] }` |
| **`$slice`** | Бере зріз масиву за індексами | `{ $slice: ["$items", 0, 3] }` |

---

### 5. Умовні оператори (Branching & Conditionals)

* **`$cond` (Тернарний оператор):**
  ```javascript
  {
    $cond: {
      if: { $gte: ["$totalPrice", 500] },
      then: "DISCOUNT_10",
      else: "NO_DISCOUNT"
    }
  }
  ```
* **`$switch` (Аналог switch-case):**
  ```javascript
  {
    $switch: {
      branches: [
        { case: { $gte: ["$points", 1000] }, then: "PLATINUM" },
        { case: { $gte: ["$points", 500] }, then: "GOLD" },
        { case: { $gte: ["$points", 100] }, then: "SILVER" }
      ],
      default: "BRONZE"
    }
  }
  ```
* **`$expr` (Вираз агрегації в запитах):**
  Дозволяє будувати порівняння між двома різними полями одного і того самого документа всередині `$match` (наприклад, знайти замовлення, де виручка перевищує собівартість: `{ $match: { $expr: { $gt: ["$totalPrice", "$costPrice"] } } }`).

## 🎯 Відповіді на питання для самоперевірки та інтерв'ю

## 1. Оптимізація `$lookup`: Чому відсутність індексу на полі `foreignField` у приєднуваній колекції здатна перетворити запит на катастрофу за продуктивністю ($O(N \times M)$)?

### 📌 Коротке резюме
* `$lookup` у NoSQL працює за принципом **Nested Loop Join** (вкладений цикл).
* Якщо на полі `foreignField` цільової колекції **немає індексу**, для кожного вхідного документа MongoDB виконує повне сканування (`COLLSCAN`) усієї приєднуваної колекції.
* Складність операції стає катастрофічною: **$\mathcal{O}(N \times M)$**, що миттєво перевантажує CPU, забиває I/O дисків та вимиває робочий кеш (WiredTiger cache).
* Наявність B-Tree індексу на `foreignField` знижує складність пошуку до **$\mathcal{O}(N \log M)$** (`IXSCAN`), прискорюючи запит у сотні або тисячі разів.

---

### 🔬 Детальний технічний механізм

```
Вхідний потік (Orders): N документів           Приєднувана колекція (Customers): M документів
┌──────────────────────────────────────┐       ┌──────────────────────────────────────────────┐
│ Doc 1 (customerId: "cust-1")         │ ───┐  │ Без індексу (COLLSCAN):                      │
├──────────────────────────────────────┤    ├─►│ Сканується ВСЯ колекція M документів!        │
│ Doc 2 (customerId: "cust-2")         │ ───┤  ├──────────────────────────────────────────────┤
├──────────────────────────────────────┤    │  │ З індексом (IXSCAN):                         │
│ Doc ...                              │ ───┤  │ Точковий пошук за B-Tree за O(log M).         │
├──────────────────────────────────────┤    │  └──────────────────────────────────────────────┘
│ Doc N (customerId: "cust-N")         │ ───┘  Разом без індексу: N * M операцій читання!
└──────────────────────────────────────┘
```

#### 1. Порівняння алгоритмічної складності та затримок:

| Параметр | Без індексу (`COLLSCAN`) | З індексом (`IXSCAN`) |
| :--- | :--- | :--- |
| **Алгоритм пошуку** | Повний перебір кожного документа в $M$ | Двійковий пошук по B-Tree дереву |
| **Складність 1 пошуку** | $\mathcal{O}(M)$ | $\mathcal{O}(\log M)$ |
| **Загальна складність** | $\mathcal{O}(N \times M)$ | $\mathcal{O}(N \log M)$ |
| **Кількість операцій** ($N=10^5, M=10^6$) | **$10^{11}$ (100 мільярдів операцій!)** | **$\approx 2 \times 10^6$ операцій** |
| **Час виконання** | Хвилини / таймаут (504 Gateway Timeout) | Лічені мілісекунди |
| **Навантаження на пам'ять** | Вимиває актуальні сторінки з RAM-кешу | Читає лише сторінки індексу |

#### 2. Що показує профільовщик `.explain("executionStats")`:
* **Без індексу:** Етап `$lookup` у звіті покаже астрономічний показник `totalDocsExamined` при невеликій кількості повернених документів `nReturned`.
* **З індексом:** `totalDocsExamined` майже дорівнює `nReturned`, а статус плану — `IXSCAN`.

> [!TIP]
> **Золоте правило NoSQL-архітектури:** Будь-яке поле, що бере участь у `$lookup` як `foreignField`, **зобов'язане мати індекс** у відповідній колекції. Якщо джоїн використовується часто під час гарячих OLTP-запитів, це чіткий сигнал розглянути часткову денормалізацію даних.

## 2. Вибух декартового добутку при `$unwind`: Чим небезпечне виконання `$unwind` для масивів великої довжини (наприклад, сотні елементів) перед важкими стадіями групування?

### 📌 Коротке резюме
* `$unwind` розмножує документи: кожен елемент масиву утворює окремий повноцінний документ, у якому дублюються всі поля батьківського об'єкта (**Document Explosion**).
* Масив із сотні елементів при вибірці у 50 000 замовлень генерує **5 000 000 проміжних документів**.
* Це призводить до вичерпання ліміту оперативної пам'яті стадії конвеєра (**100 MB RAM**), вимушеного скидання проміжних даних у файли на диск (`spill to disk`), перевантаження збирача сміття (GC) та мережевого трафіку.

---

### 🔬 Анатомія проблеми "Document Explosion"

```
1 вхідний документ (Order)                     Після $unwind по items (100 елементів)
┌────────────────────────────────────────┐     ┌────────────────────────────────────────┐
│ orderId: "ord-1", items: [100 товарів] │ ──► │ Doc 1: { orderId: "ord-1", item: 1 }   │
│ customer: { великий об'єкт клієнта }   │     │ Doc 2: { orderId: "ord-1", item: 2 }   │
│ deliveryAddress: { адреса, телефон }   │     │ ...                                    │
│ metadata: { історія змін, логи }       │     │ Doc 100: { orderId: "ord-1", item: 100}│
└────────────────────────────────────────┘     └────────────────────────────────────────┘
 Розмір: 10 КБ                                  Сумарний розмір у RAM: 100 * 10 КБ = 1 МБ!
```

#### Наслідки для продуктивності:

1. **Ліміт 100 MB RAM на стадію конвеєра:**
   Кожен проміжний етап агрегації в MongoDB має жорстке обмеження на використання пам'яті в 100 МБ. Якщо після `$unwind` стоїть стадія блокування потоку (`$group`, `$sort`), накопичення мільйонів об'єктів у RAM призведе до:
   - Падіння запиту з помилкою: `QueryExceededMemoryLimitNoDiskUseAllowed`.
   - Або, якщо ввімкнено `allowDiskUse: true`, запису гігабайтів проміжних даних на повільний диск, що збільшує час виконання запиту з часток секунди до десятків секунд.
2. **Накладні витрати пам'яті (Memory Bloat):**
   Усі важкі поля батьківського документа (адреси, статуси, історія) дублюються стільки разів, скільки елементів у масиві. Навіть якщо наступному етапу `$group` потрібна лише ціна товару, база прокачує через пам'ять гігабайти надлишкових текстових полів.

#### 🛡️ Стратегії оптимізації та запобігання:

1. **Ранній `$project` перед `$unwind`:**
   Викидайте всі зайві поля до розгортання. Залишайте лише мінімальний ідентифікатор та сам цільовий масив:
   ```javascript
   { $project: { _id: 1, items: 1 } },
   { $unwind: "$items" }
   ```
2. **Агрегація виразами масивів без `$unwind`:**
   Якщо ваша мета — порахувати загальну суму чи знайти максимальне значення всередині масиву, **не використовуйте `$unwind` + `$group`**. Використовуйте оператори масивів:
   ```javascript
   // Обчислення суми товарів прямо в документі без $unwind:
   {
     $project: {
       totalOrderPrice: { $sum: "$items.price" }
     }
   }
   ```

## 3. Обмеження пам'яті в `$facet`: Чи підтримує оператор `$facet` параметр `allowDiskUse: true` для запису тимчасових даних на диск у версіях MongoDB і які обмеження на розмір фінального BSON-документа тут діють?

### 📌 Коротке резюме
* **Підтримка `allowDiskUse`:** До версії MongoDB 6.0 підконвеєри `$facet` **не підтримували** скидання на диск (кожна гілка була жорстко обмежена 100 МБ RAM). Починаючи з **MongoDB 6.0+**, операції всередині `$facet` підтримують `allowDiskUse: true`.
* **Головне архітектурне обмеження — Ліміт BSON (16 МБ):** `$facet` завжди повертає весь результат агрегації у вигляді **одного-єдиного BSON-документа**. Якщо масиви всередині гілок перевищать сумарний обсяг **16 MB**, запит зазнає аварійного збою незалежно від налаштувань диска.

---

### 🔬 Детальний аналіз роботи `$facet`

Оператор `$facet` дозволяє виконувати кілька незалежних конвеєрів над одним і тим самим потоком вхідних документів паралельно в межах одного запиту.

```
Вхідний потік документів (Orders)
              │
              ▼
┌────────────────────────────────────────────────────────┐
│ $facet                                                 │
│ ├── categorisedByPrice: [ $bucket: { ... } ]           │ ──► Гілка 1
│ ├── topSellingProducts: [ $sort, $limit: 5 ]           │ ──► Гілка 2
│ └── revenueSummary:     [ $group: { _id: null, ... } ] │ ──► Гілка 3
└────────────────────────────────────────────────────────┘
              │
              ▼
ОДИН BSON-ДОКУМЕНТ:
{
  "categorisedByPrice": [ ... ],
  "topSellingProducts": [ ... ],
  "revenueSummary":     [ ... ]
}  ◄── ⚠️ ЖОРСТКИЙ ЛІМІТ: <= 16 MB!
```

#### Еволюція версій та поведінка `allowDiskUse`:

* **MongoDB 3.4 — 5.x:**
  Параметр `allowDiskUse: true`, переданий в `.aggregate()`, діяв на конвеєр загалом, але **ігнорувався всередині `$facet`**. Будь-який підконвеєр, що перевищував 100 МБ оперативної пам'яті (наприклад, сортування без індексу), негайно викидав помилку переповнення пам'яті.
* **MongoDB 6.0+:**
  Архітектуру `$facet` було оптимізовано. Тепер стадії всередині фасетних підконвеєрів (`$sort`, `$group`, `$bucket`) здатні записувати проміжні тимчасові файли на диск за наявності `allowDiskUse: true`.

#### Небезпека 16-мегабайтної пастки BSON:

Чому `allowDiskUse` не рятує від помилки 16 MB:
1. `allowDiskUse` дозволяє використовувати диск **лише для проміжних обчислень** під час роботи стадій.
2. Проте вихідний результат етапу `$facet` повинен запакуватися в **один BSON-документ**, ключами якого є назви гілок, а значеннями — масиви результатів.
3. Якщо одна з гілок повертає довгий список неагрегованих документів (наприклад, забули поставити `$limit` на вибірку замовлень), фінальний об'єкт вийде за межі 16 793 600 байт, і сервер поверне помилку:
   `BSONObj size: XXXXX is invalid. Size must be between 0 and 16793600(16MB)`.

> [!CAUTION]
> `$facet` створений виключно для **зведених звітів, метрик та аналітичних дашбордів** (підрахунки, групування, Top-N). Ніколи не використовуйте `$facet` для пагінації сирих даних без обов'язкового суворого лімітування (`$limit`).

## 4. Embedding vs Referencing: Чому в MongoDB часто віддають перевагу денормалізації (зберіганню імені клієнта прямо всередині замовлення), ніж постійному використанню `$lookup`?

### 📌 Коротке резюме
* **Швидкість читання ($O(1)$) та мінімізація I/O:** Вкладені дані читаються одним безперервним блоком з диска без додаткових обчислень join-логіки.
* **Історична достовірність (Point-in-Time Snapshot):** Замовлення — це юридичний чек. Ім'я, телефон та адреса клієнта на момент купівлі не повинні змінюватися, якщо клієнт оновить свій профіль через рік.
* **Шардування та горизонтальне масштабування:** `$lookup` між різними шардами створює величезне навантаження на внутрішню мережу кластера (Scatter-Gather), тоді як денормалізований документ обробляється локально на одній ноді.

---

### 🔬 Архітектурне порівняння: Нормалізація vs Денормалізація

```
Реляційний підхід (Referencing + $lookup):
┌──────────────────────────┐          ┌──────────────────────────┐
│ Order Collection         │          │ Customer Collection      │
│ _id: "ord-101"           │ ──lookup─┼─► _id: "cust-1"          │
│ customerId: "cust-1"     │          │ name: "Олександр"        │
└──────────────────────────┘          └──────────────────────────┘
 Недоліки: Додатковий дисковий I/O, небезпека зміни історичних даних, оверхед мережі при шардуванні.

Документний підхід (Embedding / Денормалізація):
┌────────────────────────────────────────────────────────────────┐
│ Order Collection                                               │
│ _id: "ord-101",                                                │
│ customer: { id: "cust-1", name: "Олександр", tier: "GOLD" }    │
└────────────────────────────────────────────────────────────────┘
 Переваги: Атомарне зчитування за O(1), гарантія незмінності історії, нульовий мережевий оверхед.
```

#### Три фундаментальні причини денормалізації:

1. **Історичний знімок стану (Point-in-Time Snapshot):**
   - У замовленні ім'я клієнта, контактний номер телефону, адреса доставки, назва купленого товару та його ціна — це **фіксація угоди в часі**.
   - Якщо в нормалізованій моделі через `$lookup` підтягувати ім'я клієнта, то при зміні прізвища користувача в системі старі замовлення за 2024 рік покажуть нове прізвище. Це порушує юридичну та фінансову звітність. Денормалізація забезпечує природну ізоляцію транзакційного знімка.

2. **Продуктивність та оптимізація кешу WiredTiger:**
   - MongoDB оптимізована для читання цілісних документів. Зчитування одного замовлення з вкладеним іменем клієнта — це одне звернення до пам'яті/диска.
   - Постійне використання `$lookup` перетворює високопродуктивну NoSQL-базу на повільний аналог реляційної системи без переваг оптимізатора CBO.

3. **Розподілена архітектура (Sharded Clusters):**
   - У розподіленому кластері колекція `orders` та колекція `customers` найчастіше розшардовані за різними ключами та знаходяться на різних фізичних серверах (шардах).
   - Виконання `$lookup` вимагає від маршрутизатора `mongos` координації cross-shard запитів: передачі списків ID по внутрішній мережі, очікування відповідей від усіх шардів та збирання результату в пам'яті. Денормалізований документ читається повністю локально з одного шарду за лічені мілісекунди.

#### ⚖️ Матриця прийняття рішень: Коли Embedding, а коли Referencing?

| Критерій | Embedding (Денормалізація) | Referencing ($lookup) |
| :--- | :--- | :--- |
| **Співвідношення читання/запис** | Читання значно переважає (Read-heavy, 90/10) | Часті оновлення спільних даних (Write-heavy) |
| **Зв'язок сутностей** | 1:1 або 1:Few (до кількох десятків) | 1:Many (тисячі), Many-to-Many |
| **Вимога до узгодженості** | Допустима eventual consistency для дубльованих полів | Потрібна сувора миттєва узгодженість одного джерела правди |
| **Розмір даних** | Не ризикує наблизитися до ліміту 16 MB | Дані постійно зростають у часі (наприклад, журнал логів) |
| **Характер даних** | Історичний знімок (Order items, Billing address) | Спільні глобальні довідники, облікові записи користувачів |
